# Context Builder：选择、预算、压缩与记忆

> 层级：核心工程。日期：2026-10-08。状态：原创机制说明设计，未实现或运行。

## 快速回顾

- 历史、当前上下文、工作状态和长期记忆具有不同生命周期。
- 上下文装配同时处理相关性、可信度、版本和预算。
- 压缩是有损变换，不能把不确定、否定或撤销授权改写成确定事实。

## 1. 信息的生命周期

| 对象 | 生命周期 | 作用 |
| --- | --- | --- |
| 完整历史/事件日志 | 可长期保留 | 追溯发生过什么 |
| 当前上下文 | 一次模型调用 | 本次决策可见的信息 |
| 工作状态 | 当前任务 | 步骤、约束、产物和待办 |
| 长期记忆/知识库 | 跨任务 | 保存可再次检索的事实 |

历史被保存不代表每次全部发送；记忆存在不代表当前模型已经看见；上下文压缩不是训练。

| 记忆类别 | 例子 | 更新方式 |
| --- | --- | --- |
| 任务/工作记忆 | 当前步骤、待处理错误 | 随任务推进，频繁更新 |
| 事实/语义记忆 | 项目版本、已确认偏好 | 带来源与有效期修订 |
| 经历/事件记忆 | 某次决策及原因 | 保留时间和上下文 |
| 程序性知识 | 某类任务步骤 | 作为文档/Skill 等维护 |

这些是功能分类，不要求分别使用四个数据库。一个 memory.md 也可能混合多类内容；文件存在并不能保证被加载、被正确检索或保持最新。

## 2. Builder 的职责与选择维度

输入是当前任务、有效规则、状态快照、可用工具、相关来源和预算；输出是满足平台协议与窗口限制的请求。它既可以使用确定性规则，也可用检索或模型辅助，但职责不是“把所有文本拼接起来”。

同一段内容可以同时“相关但不可信”“可信但过期”“重要但当前不需要”。只按向量相似度排序，不能解决指令优先级、授权变化和版本冲突。

建议把候选信息按以下维度理解：来源、时间、任务相关性、有效期、指令/数据类型、可否回读、估计 token 成本。它们不必全部暴露给模型，但需要由系统保留，以便解释为什么某条信息被选入或丢弃。

## 3. 装配过程

1. 固定必须保留的安全规则与当前用户目标。
2. 放入任务状态：已完成、待解决、明确批准范围。
3. 选择当前需要的工具定义及 Skill 片段。
4. 检索相关事实，记录来源、时间和置信程度。
5. 按信息价值与成本裁剪，保证工具调用/结果关联完整。
6. 估算 token 并预留输出和平台开销，超预算则缩减或压缩。

某段文字相关不意味着可信；相关性选择和指令优先级是不同机制。

## 4. 预算与提前规划

假设某模型允许的输入输出总预算为 32k token，团队为输出保留 4k，为平台开销与估算误差保留 2k，则应用输入目标上限为 26k。数字只是例子，不是某个实际模型规格。

再把输入分给规则、状态、工具、近期轨迹和证据。关键授权不可为腾空间而删除；大日志优先保留摘要与可回读的引用。

沿用上文虚构 32k 总预算，预留输出 4k、误差与平台开销 2k，输入目标为 26k：

| 输入类别 | 示意预算 | 裁剪约束 |
| --- | --- | --- |
| 当前规则与用户目标 | 3k | 不静默丢弃有效授权限制 |
| 结构化工作状态 | 2k | 保留进行中操作与产物版本 |
| 工具与技能说明 | 4k | 只暴露当前所需能力 |
| 近期事件 | 5k | 保留调用/结果的关联 |
| 检索证据 | 10k | 按支持度去重、保留定位 |
| 早期摘要 | 2k | 不覆盖近期明确纠正 |

合计为 26k。它不是推荐给所有系统的比例；不同服务的输入、输出、推理 token 计量方式也可能不同，接入时必须按该服务合同重新计算。

当下一步预计产生 8k 工具结果时，不能等结果到达后才发现无空间。可用分页、局部读取或保存句柄控制信息进入速度。句柄有用的前提是后续仍能访问原文，而不是创建无法兑现的引用。

不能只等 API 报上下文超限。根据预算利用率、下一步可能产生的工具输出和质量退化信号提前处理。阈值是应用策略，需要用真实任务评测，不存在所有 Agent 通用的“80% 必须压缩”。

## 5. 压缩与约束保真

压缩应保留目标、约束、关键决策、已完成步骤、失败尝试、产物 ID、未解问题及证据定位。丢掉冗余输出，不把不确定判断改写成事实。

可先裁剪可重读的大工具输出，再总结较早轨迹。摘要生成后检查：是否遗漏用户否定、是否扩大批准范围、是否丢失失败原因。压缩后仍应能回到原始记录。

自写事件序列：用户原本允许发布 r1；随后改为只审阅；工具读到 r2；一次发布请求此前已超时，是否产生副作用未知。

错误摘要：“用户希望发布最新版，资料已读取，发布失败可重试。”

较合适的摘要应保留：

```json
{
  "goal": "审阅内容",
  "allowedAction": "review_only",
  "currentRevision": "r2",
  "revokedApproval": {"revision": "r1", "action": "publish"},
  "pendingOperation": {"id": "op-9", "outcome": "unknown"},
  "nextConstraint": "先核对 op-9 状态，不自动发布",
  "evidenceRefs": ["event-12", "event-15", "tool-c4"]
}
```

压缩错误的核心不是少了几句话，而是改变了权限、时间顺序与事实确定性。摘要是一份派生数据，不能比原始事件拥有更高权威。

## 6. 长上下文、检索与缓存

长窗口允许放更多信息，但不会自动完成去重、权限过滤和版本判断；检索减少输入范围，却可能漏掉关键证据。选择取决于材料规模、任务跨度、成本与可追溯性。可以先检索候选，再把必要原文放入长上下文。

压缩与检索也不同：压缩把已有信息改写得更短；检索从外部或历史中选取信息。前者可能引入摘要失真，后者可能发生漏召回，故障诊断应分开。

KV Cache 是推理计算状态，常用于减少重复计算；产品级 prompt cache 是服务层优化；长期记忆是应用保存的知识。三者都叫“缓存/记忆”时尤其需要分清。修改前缀可能影响缓存命中，但不能为了缓存保留错误或过期规则。
