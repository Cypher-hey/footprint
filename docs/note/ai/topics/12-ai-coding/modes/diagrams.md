# AI Coding 与 Harness：把交付变成受控闭环｜概念图解

## 读图主线

AI Coding 的交付对象是受约束的代码变更及其证据；Harness 组织反馈，最终版本的实际检查比完成声明更重要。

先读整体边界，再打开内部职责或时间变化；图是简化机制模型，不是实际运行记录。所有图与系统阐述共享同一份源文件。

## 图 1：模型与工程环境之间的反馈

跟随模型决策到编译器、测试与运行环境，再回到诊断证据；反馈不是自我赞同。

[图 1：模型与工程环境之间的反馈](../figures/figure-01.mmd "footprint:figure")

这里沿用第 03 篇的反馈结构；新内容是反馈的工程含义。编译错误、测试断言和实际差异，比模型自称“已经正确”提供了更具体的修正依据，但每种证据仍有覆盖范围。

<a id="figure-02"></a>

## 图 2：证据不是一条全局“通过”标记

证据依赖代码 revision、输入和环境；‘通过’不是可以脱离版本永久复用的标签。

[图 2：证据不是一条全局“通过”标记](../figures/figure-02.mmd "footprint:figure")

修改发生在检查之后时，旧证据未必继续有效。是否需要重跑取决于变更影响范围与检查覆盖，不能简单复用一句历史上的“全部通过”。

[结合正文解释阅读](explanation.md#figure-02)

## 图没有承诺什么

- 模型自述测试通过不是测试日志。
- 目录整齐不保证依赖与状态边界清晰。
- 测试之后又改代码，需要重新评估证据有效性。
