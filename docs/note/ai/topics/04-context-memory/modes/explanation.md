## 1. Context 为什么需要被构造

**Context（上下文）**是当前模型调用实际可用的输入信息。它既可能包含聊天历史，也可能包含规则、工具定义、任务状态和检索证据。模型看见的是本轮装配结果，不是应用拥有的全部数据。

**Context Builder**是负责选择、转换和组织这些输入的应用职责。它可以是一组函数、一条管道或服务的一部分，不要求存在这个名字的类，也不是模型内部新增的神经网络模块。

### 1.1 信息的生命周期

| 对象 | 生命周期 | 作用 |
| --- | --- | --- |
| 完整历史/事件日志 | 可长期保留 | 追溯发生过什么 |
| 当前上下文 | 一次模型调用 | 本次决策可见的信息 |
| 工作状态 | 当前任务 | 步骤、约束、产物和待办 |
| 长期记忆/知识库 | 跨任务 | 保存可再次检索的事实 |

历史被保存不代表每次全部发送；记忆存在不代表当前模型已经看见；上下文压缩不是训练。

| 记忆类别 | 例子 | 更新方式 |
| --- | --- | --- |
| 任务/工作记忆 | 当前步骤、待处理错误 | 随任务推进，频繁更新 |
| 事实/语义记忆 | 项目版本、已确认偏好 | 带来源与有效期修订 |
| 经历/事件记忆 | 某次决策及原因 | 保留时间和上下文 |
| 程序性知识 | 某类任务步骤 | 作为文档/Skill 等维护 |

这些是功能分类，不要求分别使用四个数据库。一个 memory.md 也可能混合多类内容；文件存在并不能保证被加载、被正确检索或保持最新。

<a id="section-02"></a>

## 2. 选择不是只按相关性排序

输入是当前任务、有效规则、状态快照、可用工具、相关来源和预算；输出是满足平台协议与窗口限制的请求。它既可以使用确定性规则，也可用检索或模型辅助，但职责不是“把所有文本拼接起来”。

同一段内容可以同时“相关但不可信”“可信但过期”“重要但当前不需要”。只按向量相似度排序，不能解决指令优先级、授权变化和版本冲突。

建议把候选信息按以下维度理解：来源、时间、任务相关性、有效期、指令/数据类型、可否回读、估计 token 成本。它们不必全部暴露给模型，但需要由系统保留，以便解释为什么某条信息被选入或丢弃。

<a id="section-03"></a>

## 3. 从候选信息到合法请求

装配至少同时处理两种关系：信息是否值得放入，以及放入后怎样保留它的身份。前者影响质量和成本，后者影响模型能否区分事实、指令、旧状态与新结果。

### 图 2：打开 Builder 的内部职责

<a id="figure-02"></a>

[图 2：打开 Builder 的内部职责](../figures/figure-02.mmd "footprint:figure")

这里是职责分解，不强制所有实现只有一次线性处理。例如检索可以在预算不足后重新选择候选；权限检查必须在向外部服务发送数据之前完成。

一种容易理解的装配顺序是：

1. 固定必须保留的安全规则与当前用户目标。
2. 放入任务状态：已完成、待解决、明确批准范围。
3. 选择当前需要的工具定义及 Skill 片段。
4. 检索相关事实，记录来源、时间和置信程度。
5. 按信息价值与成本裁剪，保证工具调用/结果关联完整。
6. 估算 token 并预留输出和平台开销，超预算则缩减或压缩。

某段文字相关不意味着可信；相关性选择和指令优先级是不同机制。

<a id="section-04"></a>

## 4. 窗口与预算：为什么不能只在超限后截断

**上下文窗口**规定模型或服务可接纳序列的容量边界；**上下文预算**是应用在该边界内为不同信息分配的使用计划。预算小于容量并不代表浪费，因为输出、下一轮观察和平台包装也可能需要空间。

假设某模型允许的输入输出总预算为 32k token，团队为输出保留 4k，为平台开销与估算误差保留 2k，则应用输入目标上限为 26k。数字只是例子，不是某个实际模型规格。

将这个 26k 输入预算分给规则、状态、工具、轨迹和证据，可以得到以下示意。比例不是通用推荐；关键授权不可为腾空间而丢失，大日志可保留摘要和可回读引用：

| 输入类别 | 示意预算 | 裁剪约束 |
| --- | --- | --- |
| 当前规则与用户目标 | 3k | 不静默丢弃有效授权限制 |
| 结构化工作状态 | 2k | 保留进行中操作与产物版本 |
| 工具与技能说明 | 4k | 只暴露当前所需能力 |
| 近期事件 | 5k | 保留调用/结果的关联 |
| 检索证据 | 10k | 按支持度去重、保留定位 |
| 早期摘要 | 2k | 不覆盖近期明确纠正 |

合计为 26k。它不是推荐给所有系统的比例；不同服务的输入、输出、推理 token 计量方式也可能不同，接入时必须按该服务合同重新计算。

当下一步预计产生 8k 工具结果时，不能等结果到达后才发现无空间。可用分页、局部读取或保存句柄控制信息进入速度。句柄有用的前提是后续仍能访问原文，而不是创建无法兑现的引用。

不能只等 API 报上下文超限。根据预算利用率、下一步可能产生的工具输出和质量退化信号提前处理。阈值是应用策略，需要用真实任务评测，不存在所有 Agent 通用的“80% 必须压缩”。

<a id="section-05"></a>

## 5. Compaction：压缩内容，不能改写约束

**Compaction（上下文压缩）**将较大的历史表示变成较小的可用表示。常见方式包括移除可回读的大结果、抽取结构化状态、总结旧对话。它通常是有损变换：保留什么、舍弃什么，是信息选择，不只是文本缩短。

压缩应保留目标、约束、关键决策、已完成步骤、失败尝试、产物 ID、未解问题及证据定位。丢掉冗余输出，不把不确定判断改写成事实。

可先裁剪可重读的大工具输出，再总结较早轨迹。摘要生成后检查：是否遗漏用户否定、是否扩大批准范围、是否丢失失败原因。压缩后仍应能回到原始记录。

局部对照能够说明保真要求，不必依赖一条完整案例：

| 原信息中的性质 | 压缩后必须保留 | 错误简化会造成什么 |
| --- | --- | --- |
| 用户撤销了一次批准 | 已撤销及其动作范围 | 将历史意愿当当前许可 |
| 操作超时，结果未知 | 未确认的 operationId | 将未知改写成失败并重试 |
| 来源只支持特定版本 | 版本及来源定位 | 把局部结论推广到全部版本 |
| 判断仍有冲突 | 冲突双方与待核查点 | 将猜测压成确定事实 |

压缩错误的核心不是少了几句话，而是改变了权限、时间顺序与事实确定性。摘要是一份派生数据，不能比原始事件拥有更高权威。

## 6. 历史怎样继续进入下一轮

### 图 3：观察入库和上下文入模是两个动作

<a id="figure-03"></a>

[图 3：观察入库和上下文入模是两个动作](../figures/figure-03.mmd "footprint:figure")

回边沿用第 03 篇的 Agent Loop，但这里把信息处理打开：完整历史保留证据，工作状态保留当前摘要，Builder 决定哪部分进入下一次调用。并不是将 Observation 无条件粘在最后就完成了所有上下文工程。

### 6.1 长窗口、检索、压缩与缓存怎样分工

长窗口允许放更多信息，但不会自动完成去重、权限过滤和版本判断；检索减少输入范围，却可能漏掉关键证据。选择取决于材料规模、任务跨度、成本与可追溯性。可以先检索候选，再把必要原文放入长上下文。

压缩与检索也不同：压缩把已有信息改写得更短；检索从外部或历史中选取信息。前者可能引入摘要失真，后者可能发生漏召回，故障诊断应分开。

KV Cache 和前缀缓存属于 [推理系统](../../13-training-inference-systems/README.md)的计算复用机制；长期记忆属于应用信息存储。它们都能影响成本或连续性，却不能相互替代。修改前缀可能影响缓存命中，但不能为了缓存保留错误或过期规则。

本页主定义长期记忆与上下文的生命周期区别；具体如何写入、去重、解决冲突与删除，统一由 [06 RAG 与长期维护](../../06-retrieval/README.md)展开。
