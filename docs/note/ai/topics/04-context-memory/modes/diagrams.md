# Context Builder：选择、预算、压缩与记忆｜概念图解

## 读图主线

Context Builder 把系统拥有的信息变成当前调用真正可见的输入；选择、预算、身份保留与压缩保真必须一起考虑。

先读整体边界，再打开内部职责或时间变化；图是简化机制模型，不是实际运行记录。所有图与系统阐述共享同一份源文件。

<a id="figure-01"></a>

## 图 1：拥有信息与看见信息之间隔着一次选择

多种存储经过 Builder 才成为上下文；存在于系统里不代表模型此刻可见。

[图 1：拥有信息与看见信息之间隔着一次选择](../figures/figure-01.mmd "footprint:figure")

图中的四个输入可能来自不同存储。它们不会因为存在就自动进入模型；反过来，本轮进入模型的信息也不一定会长期保存。

<a id="figure-02"></a>

## 图 2：打开 Builder 的内部职责

依次看来源、选择、变换、身份组织和预算；这是职责分解，实际处理可能迭代。

[图 2：打开 Builder 的内部职责](../figures/figure-02.mmd "footprint:figure")

这里是职责分解，不强制所有实现只有一次线性处理。例如检索可以在预算不足后重新选择候选；权限检查必须在向外部服务发送数据之前完成。

[结合正文解释阅读](explanation.md#figure-02)

<a id="figure-03"></a>

## 图 3：观察入库和上下文入模是两个动作

观察分别影响历史与当前状态，再由下一轮 Builder 选择输入，不能省略这层选择。

[图 3：观察入库和上下文入模是两个动作](../figures/figure-03.mmd "footprint:figure")

回边沿用第 03 篇的 Agent Loop，但这里把信息处理打开：完整历史保留证据，工作状态保留当前摘要，Builder 决定哪部分进入下一次调用。并不是将 Observation 无条件粘在最后就完成了所有上下文工程。

[结合正文解释阅读](explanation.md#figure-03)

## 图没有承诺什么

- memory.md 存在不代表它已进入本轮输入。
- 摘要不能把历史批准变成当前许可。
- 没有所有 Agent 通用的固定压缩比例或阈值。
