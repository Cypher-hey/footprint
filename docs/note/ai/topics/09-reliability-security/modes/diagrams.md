# Agent 可靠性与安全：把权限和恢复放在模型之外｜概念图解

## 读图主线

可靠性关注任务能否被正确完成，安全关注允许边界是否被突破；二者都需要模型之外的状态、权限与结果证据。

先读整体边界，再打开内部职责或时间变化；图是简化机制模型，不是实际运行记录。所有图与系统阐述共享同一份源文件。

<a id="figure-01"></a>

## 图 1：从内容进入系统到动作离开系统

输入边界与执行边界分别回答数据能否影响判断、操作能否实际发生；两层互补。

[图 1：从内容进入系统到动作离开系统](../figures/figure-01.mmd "footprint:figure")

输入边界关心“这段内容能否被当成指令或证据”，执行边界关心“此动作能否发生”。即使前一层误判，后一层也应限制最坏影响；这就是分层防护的意义。

<a id="figure-02"></a>

## 图 2：操作意图与结果记录

检查重复意图后还要协调记录与业务写入；这张图不是 exactly-once 的证明。

[图 2：操作意图与结果记录](../figures/figure-02.mmd "footprint:figure")

图突出服务端合同：识别重复只是第一步，记录与业务效果的原子性才决定故障窗口。具体系统可能使用事务、条件写入或操作状态机，不能只根据这个图宣称 exactly-once。

[结合正文解释阅读](explanation.md#figure-02)

<a id="figure-03"></a>

## 图 3：响应丢失不等于写入失败

服务已写入而响应丢失时，查询状态比盲目再创建更能保留业务语义；前提是服务支持查询。

[图 3：响应丢失不等于写入失败](../figures/figure-03.mmd "footprint:figure")

这是理想化的支持状态查询的服务示意。实际服务不支持查询时，应按风险选择人工核对、补偿或明确阻塞，而不是声称能获得 exactly-once。

[结合正文解释阅读](explanation.md#figure-03)

## 图没有承诺什么

- 一个 UUID 不会自动使下游业务幂等。
- 补偿不一定还原时间、费用和外部可见性。
- 角色提示词和工作目录分离不自动构成安全沙箱。
