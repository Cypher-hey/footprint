## 1. 为什么 Tool、MCP 与 Skill 不是同一层

模型本身生成内容；要读取实时信息或影响环境，应用必须把可执行操作暴露为明确接口。操作接口、跨系统连接方法、任务处理知识解决三个不同问题，因此有必要分别命名。

**Tool（工具）**是可被运行时调用的操作，包含名称、输入、结果和错误约定。**MCP（Model Context Protocol）**是宿主连接外部能力与上下文的一种协议。**Skill**在这里指可发现和按需读取的任务知识包，其具体格式由宿主或相应规范决定。

### 图 1：三者在同一能力路径上的位置

<a id="figure-01"></a>

[图 1：三者在同一能力路径上的位置](../figures/figure-01.mmd "footprint:figure")

Skill 影响“怎样做”的选择，Tool 规定“调用什么”的合同，MCP 解决部分连接与消息交互。箭头没有从 Skill 直接通向外部动作，因为一份知识文档本身不是执行授权。

| 对象 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| Tool | 能执行什么操作 | 名称、输入 Schema、结果、错误 |
| MCP | 宿主怎样连接和发现外部能力 | 初始化、能力协商、请求与响应 |
| Skill | 某类任务怎样做 | 规则、步骤、示例、资源与可选脚本 |

Skill 并不自动拥有执行权限；MCP 不等于 Agent；工具也不必须通过 MCP 提供。不同产品对 Skill 的加载约定可能不同。

可以用三个反事实检查边界：没有模型，程序仍可调用工具；不用 MCP，Agent 仍可通过本地函数或 HTTP 调用工具；只有 Skill 文档而没有执行器，仍不能完成外部动作。三者可以组合，也可以分别存在。

<a id="section-02"></a>

## 2. 打开连接协议：Host、Client 与 Server

前一张图省略了连接由谁管理。MCP 在这里区分宿主、客户端与服务端，而不是把所有参与方都称为 Agent。

模型看到可用能力描述后提出调用。宿主校验参数和权限，通过本地函数或协议客户端执行。远端工具服务返回的数据再进入观察记录。

MCP 区分 Host、Client、Server；它还支持 resources 和 prompts 等能力，不只是把函数名称列出来。能协商什么能力，必须看双方实现与协议版本。

Host 管理模型交互、连接、上下文与用户控制；Client 负责一个具体 Server 的协议连接；Server 暴露能力。一个 Host 可管理多个 Client，通常由一个 Client 维护与一个 Server 的连接。模型不需要自己实现网络客户端；协议消息由宿主的软件组件处理。

### 图 2：宿主内部与外部能力的边界

<a id="figure-02"></a>

[图 2：宿主内部与外部能力的边界](../figures/figure-02.mmd "footprint:figure")

两条连接并不意味着两个 Agent。Host/Client/Server 描述协议角色；Agent 描述目标驱动决策与环境交互。角色之间的关系以所选协议版本为准。

| MCP 原语 | 主要用途 | 与 Tool 的差别 |
| --- | --- | --- |
| Tools | 调用操作 | 有参数与执行结果，可能有副作用 |
| Resources | 提供可访问的上下文资源 | 不等同于任意命令执行 |
| Prompts | 提供可复用的提示模板 | 模板存在不代表自动获得执行权限 |

初始化时声明能力，不代表所有实现都支持全部可选特性。这里按 [2025-06-18 Architecture](https://modelcontextprotocol.io/specification/2025-06-18/architecture)解释角色，不声称该版本是当前最新。

## 3. 调用提议、协议请求和业务操作怎样对应

第 03 篇的 function/tool call 是模型输出的结构化行动提议。运行时处理该提议后，可能构造一条 MCP tools/call 请求；Server 再执行某个业务操作。因此至少有模型、协议、业务三个关联层。

### 图 3：同一次动作在不同层有不同标识

<a id="figure-03"></a>

[图 3：同一次动作在不同层有不同标识](../figures/figure-03.mmd "footprint:figure")

这些标识各自解决关联问题，生命周期也不同。JSON-RPC id 用于请求与响应配对，不能自动承担业务幂等保证；业务 operationId 的语义见 [09](../../09-reliability-security/README.md)。

```json
{
  "name": "read_document",
  "input": {"documentId": "doc-42"},
  "result": {
    "ok": true,
    "revision": "r7",
    "content": "示例内容",
    "truncated": false
  }
}
```

这是应用层示意，不是 MCP 消息格式。真实协议字段按对应规范实现。documentId 比任意 URL/文件路径更容易控制权限，但服务端仍必须验证其属于当前用户。

自写工具调用例子，采用该版本的 JSON-RPC 形式：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "read_document",
    "arguments": {"documentId": "doc-42"}
  }
}
```

对应结果可以是：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "content": [{"type": "text", "text": "笔记内容示意"}],
    "isError": false
  }
}
```

参数和结果必须服从被发现的工具定义；“这个 JSON 能解析”不证明服务接受它。工具业务失败与 JSON-RPC 协议错误也应区分。字段依据见 [Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)，这里并未建立真实连接。

## 4. 工具合同：让可调用变成可理解

“处理文档”太模糊；“读取指定文档当前版本，返回 revision，不修改内容”更容易决策。描述应写输入范围、副作用、分页、错误、是否截断及恢复方式。

工具返回大对象时提供分页、字段选择或内容句柄，避免把上下文耗在无关数据上。

1. 输入合同：哪些参数允许、对象属于谁、大小和格式限制。
2. 结果合同：返回哪些字段、版本、分页与截断说明。
3. 副作用合同：是否写入、可否重复、是否需要确认。
4. 失败合同：哪些错误可重试、结果未知怎样查证。

好的描述不仅帮助模型选工具，也帮助调用方发现工具设计是否过宽。“管理所有笔记”通常不如分别定义读取、更新和发布容易审计。是否拆分仍由业务边界决定，不是工具越多越好。

<a id="section-05"></a>

## 5. Skill 的渐进披露：让过程知识按需可见

**渐进披露（Progressive Disclosure）**是先暴露足以做选择的摘要，再在相关时读取详细信息。它主要解决发现与上下文成本，不改变权限本身。

一种常见组织是名称/短描述 → 正文 → 相关附属资源。正文可以说明任务步骤、限制和判据，附件可以提供模板或脚本；应用只把当前需要的内容装入上下文。工具动态发现也不意味着每次都要重新发现已知能力。不同宿主的具体规则不同；不能把某个产品的目录约定推广为所有 Skill 标准。

正文应解释步骤和限制，脚本是可选资源。需要脚本不意味着可自动安装它的依赖；文本中声明“获得批准”也不能成为批准证据。开放发现与最小权限可以同时存在。

<a id="section-06"></a>

## 6. 能力协商不是授权

“支持什么”是协议能力问题，“谁能用什么”是权限问题，“当前是否同意做”是用户批准问题。它们可能在一次调用中同时出现，但互不代替。

工具名称里的 read-only 不是安全证明。服务端进行身份认证和对象级授权；宿主控制用户批准、网络访问及数据发送。MCP roots 的声明也不能替代操作系统沙箱。

外部工具描述可能不可信，不应允许它重新定义用户意图或要求外传凭据。

Server 宣称支持某工具，是能力；认证表明请求主体是谁；授权决定它能访问哪些对象；批准表达用户是否同意这一次具体动作。工具 annotations、名称或 Skill 描述都不能替代这些检查。

跨服务连接还需要限制数据发送目的地。A 服务返回的 URL 不能自动成为把 B 服务私有内容上传出去的授权。更多见[安全与信任边界](../../09-reliability-security/README.md)。

## 7. 版本与验证边界
