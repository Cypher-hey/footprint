## 1. Evals 在回答什么问题

**Evaluation（评测）**是在明确任务、输入条件和判据下，观察系统行为并形成质量判断的过程。**Benchmark（基准）**通常提供相对固定的任务集合和比较规则；**Metric（指标）**是将观察量化的定义。它们相关，但不是同一个东西。

一份评测首先要说明“对哪个系统、哪些任务、什么条件下的什么性质做判断”。没有这些限定，一个分数很容易被误用到它没有测过的能力。

### 图 1：评测不是只给答案打分

<a id="figure-01"></a>

[图 1：评测不是只给答案打分](../figures/figure-01.mmd "footprint:figure")

结果与行为都进入判定：答案正确却越权执行，和未越权但答错，是两种不同失败。评价规则必须先承认这种区别，才能选择合适指标。

一次成功演示不能代表可靠性。评测需要明确任务集合、成功标准、环境、模型与配置，记录重复试验和失败类型。不要在看过所有失败后，仍把这组数据叫作独立测试集。

模型能力评测、应用管道评测、Agent 轨迹评测、端到端用户任务评测，回答不同问题。评一个回答的文风，不能证明工具权限正确；检索 Recall@k 提高，也不保证用户问题解决率提高。

评测合同至少记录任务、输入分布、允许信息、预算、输出判据与禁止行为。随着任务目标改变，过去的分数可能不再可比较。

## 2. 指标与评分器：测什么，怎样测

**Rubric（评分准则）**把“好”拆为可判断的维度及等级；**Grader/Judge（评分器/评审者）**应用这些准则。准则含糊时，换成更强的评审模型也无法消除目标歧义。

| 层 | 例子 | 易误读 |
| --- | --- | --- |
| 结构 | JSON/Schema 合格率 | 合法不代表事实正确 |
| 内容 | 准确性、引用支持度 | 文风好不代表正确 |
| 行动 | 工具选择、参数正确率 | 调用成功不代表任务完成 |
| 任务 | 最终产物符合要求 | 忽略越权副作用 |
| 体验与成本 | p50/p95 延迟、总费用 | 只看成功样本的平均值 |
| 安全 | 越权率、泄露、错误执行 | 正常集通过不代表对抗集通过 |

| 方式 | 擅长 | 主要盲区 |
| --- | --- | --- |
| 确定性规则 | Schema、引用 ID、权限事件、长度 | 很难覆盖开放语义 |
| 人工判断 | 细致事实、需求理解、表达质量 | 成本、主观差异、一致性 |
| 模型评审 | 较大规模语义初筛 | 位置偏差、文风偏好、相关错误 |

模型评审应有明确 rubric，并用人工标注样本检查一致性；不能因为两个模型都同意就推断独立证据充分。评审模型也可能被候选答案中的指令干扰，候选输出仍是不可信数据。

## 3. 用例的组成与覆盖：样本为什么不只是一个问题

一条用例应包含输入、允许资料与工具、运行约束、期望性质以及禁止行为。开放任务不一定只有唯一标准答案，但仍可以定义可检验的性质，例如“结论受到来源支持”“不访问范围外资源”。

| 用例信息 | 保留原因 | 缺失后的风险 |
| --- | --- | --- |
| 任务与输入 | 确定系统要解决什么 | 对不同任务混算成绩 |
| 来源与版本 | 确定当时可知什么 | 用未来资料评价过去结果 |
| 环境与权限 | 确定允许什么 | 无法判断拒绝是否正确 |
| 期望性质 | 确定内容或产物质量 | 只凭总体印象打分 |
| 禁止行为 | 单独表达硬边界 | 平均分掩盖严重错误 |
| 配置与预算 | 确定可比较条件 | 用不同成本换来的成绩直接比较 |

覆盖应由任务分布和风险驱动，包括常见输入、缺证据、冲突资料、长上下文、异常返回和越权诱导。不能因为边界样本难准备就只测正常路径，也不能只测攻击样本后声称日常可用性良好。

## 4. 比较与统计：观察到差异，不等于证明普遍提升

保持任务、工具、数据和预算条件一致，一次只改变主要变量。比较模型时同时记录成功率、成本和耗时；比较 RAG 时检查检索质量；比较多 Agent 时计入协调成本。

小样本中一两条差异可能是偶然。样本数、重复次数和配对关系影响估计的不确定性。置信区间是在特定抽样假设下表达估计范围的统计工具，不是“模型有多少把握”的主观分数，也不能修复不具代表性的任务集。

自写假设：同一组 20 题，A 对 15 题，B 对 17 题。只能先说观察到 75% 与 85%；这是增加 10 个百分点，不是“增加 10%”。相对增幅约 13.3%，但小样本不证明真实提升。

逐题配对还要保留哪些 A 对 B 错、哪些 A 错 B 对。重复运行用于观察随机波动；同一任务的多次结果不是同等数量的独立新任务，统计解释应考虑这种关联。

成本分母也要明确：每请求费用与每个成功任务费用不同。重试、失败、工具调用和并行分工的消耗都应计入完整任务成本。

用失败案例改提示后，这些案例成为开发依据；若仍称它们为未见测试集，就混淆了评测角色。可保留独立集合，并记录新任务分布和版本变化。[机器学习基础](../../15-machine-learning/README.md)中的数据泄漏同样适用于应用评测。

## 5. 如何阅读报告：质量、风险与成本不能互相冒充

下表为自写假设数据，不是本仓库真实实验：

| 维度 | 方案 A | 方案 B | 可支持的判断 |
| --- | --- | --- | --- |
| 结构合法 | 20/20 | 20/20 | 这组样本上结构无差异 |
| 事实通过 | 15/20 | 17/20 | B 多通过两条，仍需看配对与波动 |
| 引用支持 | 14/20 | 16/20 | 需确认漏引用与错误引用分别多少 |
| 越权动作 | 0/20 | 1/20 | B 出现硬约束失败，不能被平均分抵消 |
| 总费用 | 假设较低 | 假设较高 | 还需按成功任务成本衡量 |

只展示 17/20 会隐藏越权；只展示 0 次越权，也不能证明系统对所有攻击安全。样本范围与风险等级决定结论能推广多远。

## 6. 可观测性：从分数回到发生过的事情

**可观测性（Observability）**让系统通过外部可取得的记录暴露运行状况。评测回答“表现如何”，观测帮助回答“为什么这样”。记录了很多数据不代表已有正确的评测方法。

| 对象 | 组织方式 | 用途 |
| --- | --- | --- |
| Log | 某处发生的事件记录 | 查看局部错误或状态 |
| Trace | 按一次请求/任务关联的调用轨迹 | 还原跨组件因果和耗时 |
| Metric | 多次运行聚合后的数值 | 比较分布、趋势和异常 |

### 图 3：把任务级失败下钻到阶段

<a id="figure-03"></a>

[图 3：把任务级失败下钻到阶段](../figures/figure-03.mmd "footprint:figure")

Trace 需要能关联各阶段，但不需要把全部私人原文复制到每个记录。数据最小化与日志访问控制由 [09](../../09-reliability-security/README.md)展开。

```json
{
  "taskId": "eval-07",
  "runId": "run-3",
  "step": 4,
  "event": "tool_completed",
  "tool": "read_document",
  "durationMs": 120,
  "status": "ok",
  "artifactRevision": "r2"
}
```

这是虚构示例。真实日志还需模型/提示词/工具版本、预算、停止原因与来源定位；不记录无必要的秘密或私人原文。

有用的 trace 关联：任务 ID、运行 ID、模型/提示版本、工具版本、来源 revision、调用/结果 ID、耗时、预算、停止原因和产物版本。尽量记录可观察行为与必要证据，不以保存完整私人内容为默认。

## 7. 归因：把失败转成可检验的改进假设

失败可能来自任务含糊、检索漏召回、上下文裁剪、模型判断、工具契约、环境故障或验收器错误。先归因，再决定改提示、工具或模型，避免所有问题都升级模型。

```text
任务失败
├─ 目标/判据不清楚
├─ 资料或权限不可用
├─ 检索、裁剪或版本错误
├─ 模型判断或生成错误
├─ 工具/环境执行失败
├─ 状态、重试或副作用处理错误
└─ 评分器或人工标注错误
```

一次失败可能跨多层。归因不是为了把责任推给某一层，而是定位下一次修改应改变什么，并避免把多个变量同时改动后无法解释结果。

把真实失败整理成去敏测试。开发集用于改进，保留集用于观察泛化；定期补新分布。上线前门禁不能只检查平均质量，还要检查高风险禁止行为。
