## 1. RAG 为什么存在：生成所需信息不全在参数中

**RAG（Retrieval-Augmented Generation，检索增强生成）**将检索得到的外部信息作为生成条件。对资料会变化、需要精确引用或包含私有领域事实的任务，参数内的规律不必然足以支持当前结论；外部证据提供了一条可更新、可定位的信息路径。

<a id="figure-01"></a>

[图 1：先看检索增强的最小关系](../figures/figure-01.mmd "footprint:figure")

增强发生在输入条件上，不要求每次重新训练模型。图中从候选到回答的箭头只表示信息被提供，不保证模型准确使用了证据。

RAG 让生成过程使用外部检索证据；长期记忆保存跨任务有用的信息。它们可以共享存储与检索组件，但不等价。用户偏好、项目事实和公开知识需要不同的权限与更新策略。

## 2. 表示与索引：系统怎样“找得到”

检索并不是必须使用向量数据库。关键词检索按词项匹配与统计信号排序；向量检索把查询和片段编码成可比较的向量，再按相似度寻找候选；结构化查询利用明确字段与关系过滤。

**Embedding（嵌入）**是对象的向量表示，基础概念见 [16](../../16-language-models/README.md)。在检索里，关键是查询与文档的表示是否在兼容空间中可比较。不同模型产生的向量不能仅因为维度相同就直接混在同一个语义索引里。

**相似度**衡量表示的接近程度。常用余弦相似度为 dot(q,d)/(norm(q)×norm(d))，比较方向而非向量长度；它不是“这段材料支持答案”的概率。数值高的片段仍可能讨论相反结论、不同版本或同名对象。

**索引（Index）**是用于加速查找的数据结构。向量只是被索引的表示之一；文档标识、来源、版本和权限仍需独立保存。近似最近邻检索会用召回与资源之间的取舍加快搜索，不能假定永远找到精确全局最邻近项。

## 3. Chunk：检索单元为什么会改变答案边界

**Chunk（分块）**是一次检索、排序或引用所处理的内容单元；这里不是网络传输的一块字节。分块决定模型最终可能看到哪些定义、条件与例外，因此它不仅是性能参数，也影响结论的完整性。

以标题、段落、代码单元和业务对象为边界，保留文档 ID、版本、路径及上下文关系。小块容易失去定义，大块容易带入噪音。最优大小由查询和数据决定，不能固定“每 500 字最优”。

```json
{
  "chunkId": "cache-r3-02",
  "documentId": "cache",
  "revision": "r3",
  "heading": "no-store",
  "text": "用于说明的片段",
  "sourceLocation": "path + commit + section",
  "validFrom": "2026-10-01",
  "accessScope": "由服务端解释的权限标识"
}
```

chunk ID 用于引用，document ID 表达归属，revision 表达版本。仅存一段文本和向量，会使更新去重、冲突判断和来源追踪变难。访问范围字段不是可让模型自行填写的授权凭据。

分块会改变检索对象：定义与例外被切开时，命中定义可能产生错误的全称结论；整章作为一个块又可能稀释相关信息。保留父子关系、相邻段落与标题路径，有助于检索后补充上下文。

## 4. 召回与重排：先找到，再判断顺序

**召回（Retrieval）**从大范围中取得候选；**重排（Reranking）**再对有限候选做更细的相关性判断。重排不能恢复根本没召回的材料，而增加候选数量也不意味着最终上下文应全部塞满。

| 方式 | 优点 | 典型失败 |
| --- | --- | --- |
| 关键词/BM25 | 精确术语、错误码、标识符 | 同义表达漏召回 |
| 稠密向量 | 语义近似 | 相似但不支持结论 |
| 混合检索 | 兼顾多种信号 | 融合权重需验证 |
| 重排 | 改善候选顺序 | 增加成本与延迟 |
| 图/结构化索引 | 明确实体关系与路径 | 构建和更新复杂 |

知识图谱不是向量检索的必然升级；先证明问题需要关系推理，再承担维护成本。

| 需求 | 优先检查 | 不能单独解决的部分 |
| --- | --- | --- |
| 最新可引用事实 | 检索、版本与来源 | 固定权重不会自动更新 |
| 少量完整材料跨段分析 | 长上下文与装配质量 | 窗口更长不保证正确利用 |
| 稳定风格或重复行为 | 示例、提示、必要时适配 | 不保证实时知识完整 |
| 复杂对象关系 | 结构化查询/图关系 | 向量相似不是精确关系运算 |

## 5. 从相似片段到证据：Grounding 的关键一步

**Grounding（证据支撑）**在这里指让生成结论与可定位来源建立支持关系。一个来源可以真实存在却不支持当前断言；一个答案也可以偶然正确却无法被所引材料证明。因此真实性、相关性和支持度要分开。

### 图 3：来源与结论之间需要可检查的映射

<a id="figure-03"></a>

[图 3：来源与结论之间需要可检查的映射](../figures/figure-03.mmd "footprint:figure")

引用标识只解决“指向哪里”；片段到断言的箭头才需要检查“是否支持”。缺少这条支持关系时，添加更多链接也不能把生成文本变成可靠知识。

答案中的每个关键结论应可定位到来源。搜索命中、读到正文、来源可信、结论被支持是四个不同关卡。来源冲突时保留冲突和时间，而不是强行拼成一致说法。

对 Footprint，可用 path + commit SHA + heading + excerpt 保存证据，避免引用随主分支变化而失效。

自写问题：“no-cache 是否表示不能存储？”

| 阶段 | 观察 | 判断 |
| --- | --- | --- |
| 召回 | 只找到 no-store 页面 | 查询理解或索引覆盖不足 |
| 重排 | 正确段落在候选中，被排出预算 | 排序或证据配额问题 |
| 装配 | 标题存在，关键例外被截断 | 上下文裁剪问题 |
| 生成 | 原文已说明可存储，答案却否认 | 生成利用证据失败 |
| 引用 | 答案正确，却引用无关段落 | 引用映射/支持度问题 |

因此“换一个更强模型”不一定解决前面三个阶段。故障归因应保存阶段产物，不能只有最终答案截图。

## 6. 长期记忆：存下来以后怎样保持可用

[04](../../04-context-memory/README.md)定义了长期记忆与当前上下文的生命周期区别。这里关注维护：存储只是开始，后续必须能判断信息是否仍有效、与什么对象有关、何时应被更新或删除。

事实、来源时间、有效期、实体和情境一起决定信息的可用范围。新旧记录冲突时，需要判断是事实变化、版本不同、情境不同，还是提取本身错误。

敏感信息按最少必要原则保存，不保存无必要的秘密。记忆中的历史批准不能无条件升级为当前授权。

记忆写入可理解为：提取候选 → 判断是否值得长期保存 → 绑定来源/时间 → 解决冲突 → 更新检索入口。一次临时选择不应直接变成长期偏好。

冲突并不一定要覆盖：同一人在工作与个人项目中可能偏好不同工具；同一技术规则在不同版本下也可同时有效。实体、时间和情境比单一“最新文本”更重要。

删除还涉及索引、缓存、摘要和备份策略。工程上应说明哪些副本会何时失效，不能因为删了数据库一行就宣称所有派生数据立即消失。

## 7. 阶段指标怎样定位不同故障

本节只定义检索特有指标；评测集合、评分器、统计比较与观测方法集中在 [10 Evals](../../10-evaluation/README.md)。

分开评测召回、相关性、答案忠实性与引用准确率。若正确文档根本没检索到，换提示词可能无效；若证据已在上下文但仍编造，问题在生成或约束。

Recall@k 是前 k 个候选中相关项数占全部标注相关项数的比例；Precision@k 是其中相关项数占所评估候选数的比例，固定返回 k 个时分母为 k。MRR 对多个查询取首个相关结果排名倒数的平均；nDCG 根据分级相关性和位置折损评价排序，并按理想排序归一化。它们需要明确标注准则；不同任务的“相关”不能混用。

答案层另看真实性、证据忠实性、引用支持度与覆盖。答案与来源一致，来源仍可能过期；引用真实 URL，段落仍可能不支持断言。检索命中、来源可靠、结论成立要分别判断。

若资料库没有答案，适当说明缺证据是一种有效行为；不能为了提高“回答率”强行生成。
