## 1. 从知识列表到系统关系

独立理解 Tool、Context、Workflow 之后，还需要知道它们在同一次任务中怎样互相约束。否则容易出现“每个词都认识，但不知道为什么需要它”的断裂。

本页不引入新的核心组件，而是把前面章节连接到三个共同问题：

1. **信息问题**：当前决策依据什么，来源和版本是什么？
2. **控制问题**：谁决定下一步，哪些动作允许发生，何时停止？
3. **证据问题**：输出或动作结果怎样被确认，结论能推广到哪里？

同一个组件可能参与多个问题。例如 Context Builder 既选择信息，也保留有效约束；工具既产生外部观察，也可能造成副作用。划分视角有助于分析，不意味着职责完全互斥。

## 3. 第二层全景：信息流与控制流不相同

### 图 2：把职责之间的输入输出展开

<a id="figure-02"></a>

[图 2：把职责之间的输入输出展开](../figures/figure-02.mmd "footprint:figure")

信息流描述“什么成为下一步输入”，控制流描述“下一步是否允许发生”。外部结果进入状态，不代表所有结果必须立即再次调用模型；运行时可能等待用户、核对未知操作或结束任务。

图中的回边是第 03 篇已经定义的 Agent Loop。这里的新增认知是它与来源、权限和产物边界的关系，而不是又定义一种循环。固定流程和单次请求可以只使用这张图的子集。

## 4. 不同应用形态怎样取用这些机制

| 形态 | 谁主要决定路径 | 信息需求 | 主要边界 |
| --- | --- | --- | --- |
| 单轮文本处理 | 调用方程序 | 当前材料与指令 | 输出与业务校验 |
| 固定检索问答 | 预设检索/生成流程 | 外部证据 | 来源、权限、支持度 |
| 固定工作流 | 程序定义步骤与条件 | 各步骤所需输入 | 状态转换与恢复 |
| 工具型 Agent | 模型在约束内动态选择 | 历史、观察与按需来源 | 行动权限、预算、停止 |
| 多 Agent 协作 | 协调规则与各局部决策 | 分派与共享证据 | 依赖、冲突、最终责任 |

这里是常见组织方式，实际系统可以混合。固定工作流某个节点可以运行 Agent，Agent 也可以调用一个内部固定流程的工具。

“自主程度更高”不是“技术更先进”的充分条件，也不是风险大小的唯一决定因素。固定脚本可以执行高影响写操作；只读系统也可能泄露数据。风险首先取决于所接触的数据与所允许的动作。

## 5. 第三层全景：内容、运行和权限具有不同身份

跨章关系中反复出现 documentId、runId、revision、operationId。它们并不是需要全部照抄的字段清单，而是对不同对象身份的表达。

### 图 3：一份产物与三类相关记录

<a id="figure-03"></a>

[图 3：一份产物与三类相关记录](../figures/figure-03.mmd "footprint:figure")

来源版本回答“依据哪份材料”，产物版本回答“修改了什么”，运行记录回答“怎样得到”，批准回答“允许什么”，操作结果回答“发生了什么”。同一个字符串不能自动兼任所有身份。

| 对象 | 应表达的事实 | 不应混作 |
| --- | --- | --- |
| Source / Excerpt | 原材料和可定位片段 | 模型生成的结论 |
| Draft / Revision | 内容及其特定版本 | 执行成功状态 |
| Run / Observation | 一次运行与接收的反馈 | 永久正确的事实 |
| Approval | 对特定动作和范围的有效许可 | 模型自称获准 |
| Operation | 外部动作的意图及结果 | 界面的 loading 标志 |

这是一种分析模型，不要求分别创建数据库表。它的作用是防止版本、权限和状态在不同章节或实现中被混用。

## 6. 故障怎样沿知识关系定位

系统症状与根因不是一对一关系。“回答错误”可能来自资料错误、检索遗漏、上下文裁剪或模型误用；“没有完成”可能来自运行控制、工具状态或界面呈现。

| 症状 | 先区分哪些事实 | 对应知识入口 |
| --- | --- | --- |
| 没用到已保存资料 | 是否检索到、是否进入本轮输入 | [06](../../06-retrieval/README.md) → [04](../../04-context-memory/README.md) |
| 有引用但结论不成立 | 来源真实与支持当前断言是否混淆 | [06](../../06-retrieval/README.md) → [10](../../10-evaluation/README.md) |
| 结果结构合法却不可用 | 字段、业务语义、引用图或版本哪里失败 | [02](../../02-inference/README.md) → [07](../../07-ui-ir/README.md) |
| 已取消却产生外部效果 | 本地生命周期与远端操作是否被混同 | [08](../../08-workflow-state/README.md) → [09](../../09-reliability-security/README.md) |
| 增加 Agent 后更慢 | 依赖、共享瓶颈和汇总成本 | [11](../../11-multi-agent/README.md) → [10](../../10-evaluation/README.md) |
| 模型部署内存不足 | 权重、KV、并发和临时开销 | [13](../../13-training-inference-systems/README.md) |
| AI 说测试通过但仍出错 | 是否有实际日志，是否绑定最终版本 | [12](../../12-ai-coding/README.md) → [10](../../10-evaluation/README.md) |

箭头表示分析时可以接续的知识关系，不是固定排障脚本。没有相关观察证据时，应先承认不确定，不能凭熟悉某个框架就把所有问题归给它。

## 7. Base 与 Advance 怎样连续扩展

Base 建立对象、机制、条件与相邻概念的关系。Advance 应回答更窄、更深的问题，例如“压缩如何保持否定约束”“近似检索怎样影响特定分布”“KV 分页怎样改变内存利用率”。

两者的区别不在字数或术语多少：

| Base 应解释 | Advance 在此基础上补充 |
| --- | --- |
| 它是什么，解决什么问题 | 明确的问题变体与假设 |
| 完整的最小机制 | 数学推导、实现细节或实测分析 |
| 关键边界与易混对象 | 失效条件、方案比较与反例 |
| 与其他概念怎样连接 | 跨专题组合产生的新问题 |

当前 [ADVANCE](../../../ADVANCE.md)是问题与资料入口，不冒充已完成的高级正文。新的知识点先找到主定义归属，再决定补入已有章节还是拆出专题，避免建立第二份同名百科。
