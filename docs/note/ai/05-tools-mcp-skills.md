# 工具、MCP 与 Skills：三种不同的能力边界

> 层级：核心工程。日期：2026-10-08。协议示例依据 MCP 2025-06-18，不声称它是最新版本。
> 状态：协议与概念核查；未连接 MCP Server 或执行工具。

## 快速回顾

- Tool 提供能力，MCP 提供连接协议，Skill 提供过程知识。
- 能力协商、身份认证、对象授权与用户批准不是同一步。
- 协议请求 ID、模型调用 ID 与业务操作 ID 需要明确映射。

## 1. 能力、协议与过程知识

| 对象 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| Tool | 能执行什么操作 | 名称、输入 Schema、结果、错误 |
| MCP | 宿主怎样连接和发现外部能力 | 初始化、能力协商、请求与响应 |
| Skill | 某类任务怎样做 | 规则、步骤、示例、资源与可选脚本 |

Skill 并不自动拥有执行权限；MCP 不等于 Agent；工具也不必须通过 MCP 提供。不同产品对 Skill 的加载约定可能不同。

假设需要读一篇笔记并核查术语：

- Tool 是 read_note(id)：提供实际读取能力，规定参数、返回值与错误。
- MCP 是把这项能力提供给外部宿主的一种协议方式；相同操作也可以是本地函数或普通 HTTP API。
- Skill 是“核查术语时先确认版本，再找官方依据，再标注不确定项”的过程知识；它可指导使用 read_note，但不因此获得读取任意笔记的权限。

如果没有模型而由程序固定调用 read_note，工具仍然存在；如果不用 MCP，Agent 仍可调用工具；只有 Skill 文档而没有执行器，也不能自动完成外部动作。

## 2. MCP 角色与能力协商

模型看到可用能力描述后提出调用。宿主校验参数和权限，通过本地函数或协议客户端执行。远端工具服务返回的数据再进入观察记录。

MCP 区分 Host、Client、Server；它还支持 resources 和 prompts 等能力，不只是把函数名称列出来。能协商什么能力，必须看双方实现与协议版本。

Host 管理模型交互、连接、上下文与用户控制；Client 负责一个具体 Server 的协议连接；Server 暴露能力。一个 Host 可管理多个 Client，不能把 Host、Client、Server 都笼统叫“Agent”。

| MCP 原语 | 主要用途 | 与 Tool 的差别 |
| --- | --- | --- |
| Tools | 调用操作 | 有参数与执行结果，可能有副作用 |
| Resources | 提供可访问的上下文资源 | 不等同于任意命令执行 |
| Prompts | 提供可复用的提示模板 | 模板存在不代表自动获得执行权限 |

初始化时声明能力，不代表所有实现都支持全部可选特性。这里按 [2025-06-18 Architecture](https://modelcontextprotocol.io/specification/2025-06-18/architecture)解释角色，不声称该版本是当前最新。

## 3. 应用合同与协议消息

```json
{
  "name": "read_document",
  "input": {"documentId": "doc-42"},
  "result": {
    "ok": true,
    "revision": "r7",
    "content": "示例内容",
    "truncated": false
  }
}
```

这是应用层示意，不是 MCP 消息格式。真实协议字段按对应规范实现。documentId 比任意 URL/文件路径更容易控制权限，但服务端仍必须验证其属于当前用户。

自写工具调用例子，采用该版本的 JSON-RPC 形式：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "read_note",
    "arguments": {"id": "note-a"}
  }
}
```

对应结果可以是：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "content": [{"type": "text", "text": "笔记内容示意"}],
    "isError": false
  }
}
```

协议请求 id 用于连接层关联；应用的 runId、模型工具调用 callId 和业务 operationId 有各自生命周期，不能假定全都同一个值。工具业务失败与 JSON-RPC 协议错误也应区分。字段依据见 [Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)，这里并未建立真实连接。

## 4. 工具描述与四类合同

“处理文档”太模糊；“读取指定文档当前版本，返回 revision，不修改内容”更容易决策。描述应写输入范围、副作用、分页、错误、是否截断及恢复方式。

工具返回大对象时提供分页、字段选择或内容句柄，避免把上下文耗在无关数据上。

1. 输入合同：哪些参数允许、对象属于谁、大小和格式限制。
2. 结果合同：返回哪些字段、版本、分页与截断说明。
3. 副作用合同：是否写入、可否重复、是否需要确认。
4. 失败合同：哪些错误可重试、结果未知怎样查证。

好的描述不仅帮助模型选工具，也帮助调用方发现工具设计是否过宽。“管理所有笔记”通常不如分别定义读取、更新和发布容易审计。是否拆分仍由业务边界决定，不是工具越多越好。

## 5. Skill 的发现与渐进读取

常驻能力摘要，选中后读取完整 Skill，再按需访问附件。这样可以降低无关上下文，但必须保留必要权限规则。工具动态发现不意味着每次都要重新发现已知能力。

典型设计是先提供名称与短描述，匹配到任务后读取正文，再读取相关附属资源。不同宿主的具体规则不同；不能把某个产品的目录约定推广为所有 Skill 标准。

正文应解释步骤和限制，脚本是可选资源。需要脚本不意味着可自动安装它的依赖；文本中声明“获得批准”也不能成为批准证据。开放发现与最小权限可以同时存在。

## 6. 能力、身份与批准

工具名称里的 read-only 不是安全证明。服务端进行身份认证和对象级授权；宿主控制用户批准、网络访问及数据发送。MCP roots 的声明也不能替代操作系统沙箱。

外部工具描述可能不可信，不应允许它重新定义用户意图或要求外传凭据。

Server 宣称支持某工具，是能力；认证表明请求主体是谁；授权决定它能访问哪些对象；批准表达用户是否同意这一次具体动作。工具 annotations、名称或 Skill 描述都不能替代这些检查。

跨服务连接还需要限制数据发送目的地。A 服务返回的 URL 不能自动成为把 B 服务私有内容上传出去的授权。更多见[安全与信任边界](09-reliability-security.md)。

## 7. 版本与验证边界
