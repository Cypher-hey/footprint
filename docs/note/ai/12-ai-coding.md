# AI Coding 与 Harness：把交付变成受控闭环

> 层级：工程实践。日期：2026-10-08。状态：流程设计，无自动开发任务执行。

## 快速回顾

- Prompt、Context、Tools、Runtime 与 Harness 的职责相关但不同。
- 代码产物只是中间结果，交付结论需要最终版本的验证证据。
- 项目印证应沉淀可迁移机制，不能把一次成功升级为普遍保证。

## 1. Harness 与相邻职责

Harness 是模型周围的运行、工具、状态与验证设施。提示词是其中一部分；仓库导航、工具协议、权限、失败恢复和验收也会影响结果。

AI 写出代码只是中间产物，任务完成还要有可审阅的 diff、测试证据和交付边界。

| 概念 | 主要关注 | 不负责包办 |
| --- | --- | --- |
| Prompt | 本次任务说明和输出要求 | 文件系统与权限隔离 |
| Context Engineering | 为决策选择并组织信息 | 所有外部操作的执行 |
| Tools | 可调用能力与合同 | 全局任务规划 |
| Agent Runtime | 循环、状态、预算与工具调度 | 自动证明业务正确 |
| Harness | 围绕模型的运行、约束、评估设施 | 保证模型永不出错 |
| Repository Architecture | 代码职责、依赖、可导航性 | 某个模型的私有行为 |

Harness 的边界在不同项目中并不完全一致。使用该词时应说明具体包含什么，不能把它当成统一标准产品。模型能力提升可能改变哪些约束需要显式实现，但权限、外部状态和验收事实不会因此自动消失。

## 2. 仓库与上下文质量

理解现状 → 最小计划 → 小范围修改 → 本地验证 → 独立审阅 → 交付 → 观察。失败时回到具体证据，不是继续扩大修改范围。

代码上下文应包括入口、数据流、约束和相关测试，不能仅把整个仓库塞入窗口。目录可导航、职责明确、可独立测试的模块同时帮助人和 AI。

清晰入口减少寻找成本；明确模块边界减少不必要改动；类型和契约使错误更早暴露；测试和可重现环境提供反馈。它们同时帮助人类开发，并非只为 AI 服务。

反过来，目录很整齐也不等于真实职责清晰。若跨层隐式依赖多、状态可从任意位置写入，模型读少量文件可能建立错误假设。上下文导航应跟随调用和数据依赖，而不只按文件大小截取。

## 3. 任务合同

| 项目 | 要回答的问题 |
| --- | --- |
| 目标 | 改善什么行为 |
| 范围 | 哪些目录、哪些功能 |
| 非目标 | 哪些内容不动 |
| 约束 | 版本、性能、安全、兼容 |
| 验收 | 怎样证明正确 |
| 权限 | 是否允许提交、推送、发布 |
| 预算 | 模型、时间与费用上限 |

| 项目 | 内容 |
| --- | --- |
| 目标 | 旧 run 的响应不得覆盖当前卡片 |
| 范围 | 请求状态与回包归属校验 |
| 非目标 | 不改 UI 框架、不重写数据层 |
| 约束 | 保留现有接口与取消行为 |
| 证据 | 复现描述、最小 diff、相关断言与最终 revision |
| 权限 | 代码修改与提交范围单独约定，发布需另行授权 |

合同不是把所有未来细节锁死；发现范围不够时应说明证据并调整，而不是悄悄把小 bug 变成全量重构。

## 4. 一次变更的知识链路

自写案例：修正“取消生成后旧结果覆盖新卡片”的问题。

1. 目标是结果归属，不只是隐藏 loading。
2. 相关上下文包括请求创建、取消、回包处理、状态保存和渲染选择。
3. 机制候选是 runId/revision 校验；它解决迟到回包，但不自动取消远端副作用。
4. 验证需覆盖正常完成、取消、立即重启、旧结果晚到和重复事件。
5. 交付证据应绑定最终版本；如果测试后又改回包逻辑，旧证据不再充分。

这个案例连接[状态机](08-workflow-state.md)、[恢复](09-reliability-security.md)与[评测](10-evaluation.md)，不要求在知识仓库里创建应用。

## 5. 验证证据与 Review

类型检查发现部分静态错误；单元测试检查局部逻辑；集成测试检查边界；浏览器/设备测试检查真实交互；性能测试检查代价。每种检查有盲区，不能互相冒充。

记录最终提交 SHA 与测试对象。测试后又改代码，应重跑受影响检查。

类型通过可能仍有业务错误；单元测试通过可能遗漏真实依赖；浏览器页面看起来正常可能掩盖权限问题。每一层只能支持它观察到的结论。

审查应核对实际 diff、调用路径和执行证据，而不是只读模型生成的完成说明。失败日志也要保留环境信息，否则无法区分代码缺陷、依赖版本和测试环境问题。

查看异常路径、资源清理、输入校验、权限扩张、新依赖、兼容性和回退。不要让 AI 仅总结自己的 diff 充当独立 Review。

AI 输出“测试通过”不是日志；需要执行证据。不能因为修改是文档就忽略错误命令或过时安全建议。

对 Footprint：文件清单覆盖、标题层级、代码围栏、内部链接、引用来源、版本标注、图表可读性和旧结论清理分别检查。读取了所有文件不等于检查了全部事实。

## 6. 经验回流与深入入口

适合写回的是稳定机制与可迁移教训：为什么 runId 必要、取消与撤销有什么区别、怎样观察过期响应。项目特有文件路径和命令可以放“印证记录”，并绑定版本。

一次修复成功不足以证明“所有竞态都已解决”。知识条目应保存结论范围、反例和来源；敏感日志和生产凭据不属于印证材料。

怎样衡量仓库可导航性？哪些验证可以自动化，哪些必须依赖业务判断？模型如何利用编译器、测试和运行日志？这些可进入 Advance 的 AI-Native Engineering 专题，避免把工具列表当工程方法。
