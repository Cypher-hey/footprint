# AI Coding 与 Harness：把交付变成受控闭环

> Base / AI-Native Engineering。核查：2026-10-08。概念与机制说明，没有自动开发任务执行。
> 衔接：本页把 [Loop](03-agent-loop.md)、[上下文](04-context-memory.md)和[评测](10-evaluation.md)放到代码变更中，解释它们怎样共同支持交付。

## 快速回顾

- Prompt、Context、Tools、Runtime 与 Harness 的职责相关但不同。
- 代码产物只是中间结果，交付结论需要最终版本的验证证据。
- 项目印证应沉淀可迁移机制，不能把一次成功升级为普遍保证。

## 1. AI Coding 为什么需要模型之外的设施

**AI Coding**涵盖模型辅助理解、生成、修改和验证代码。补全一段文本与执行完整代码变更并不是同一级任务；后者涉及仓库状态、构建环境、约束和可观察结果。

**Harness**在这里指围绕模型组织运行、工具、状态、约束与验证的设施。它的边界因项目而异，不是统一标准组件，也不必是一套大型框架。

### 图 1：模型与工程环境之间的反馈

```mermaid
flowchart LR
    C["需求、代码与约束"] --> M["模型决策"]
    M --> H["Harness：检查与调度"]
    H --> E["仓库、编译器、测试和运行环境"]
    E --> O["诊断与产物证据"]
    O --> C
```

这里沿用第 03 篇的反馈结构；新内容是反馈的工程含义。编译错误、测试断言和实际差异，比模型自称“已经正确”提供了更具体的修正依据，但每种证据仍有覆盖范围。

AI 写出代码只是中间产物，任务完成还要有可审阅的 diff、测试证据和交付边界。

| 概念 | 主要关注 | 不负责包办 |
| --- | --- | --- |
| Prompt | 本次任务说明和输出要求 | 文件系统与权限隔离 |
| Context Engineering | 为决策选择并组织信息 | 所有外部操作的执行 |
| Tools | 可调用能力与合同 | 全局任务规划 |
| Agent Runtime | 循环、状态、预算与工具调度 | 自动证明业务正确 |
| Harness | 围绕模型的运行、约束、评估设施 | 保证模型永不出错 |
| Repository Architecture | 代码职责、依赖、可导航性 | 某个模型的私有行为 |

Harness 的边界在不同项目中并不完全一致。使用该词时应说明具体包含什么，不能把它当成统一标准产品。模型能力提升可能改变哪些约束需要显式实现，但权限、外部状态和验收事实不会因此自动消失。

## 2. 仓库可导航性怎样影响变更质量

代码变更需要先建立足够准确的依赖模型，再决定修改范围。找错入口、漏看副作用或误解状态归属，会让局部看似合理的补丁破坏其他路径。

代码上下文应包括入口、数据流、约束和相关测试，不能仅把整个仓库塞入窗口。目录可导航、职责明确、可独立测试的模块同时帮助人和 AI。

清晰入口减少寻找成本；明确模块边界减少不必要改动；类型和契约使错误更早暴露；测试和可重现环境提供反馈。它们同时帮助人类开发，并非只为 AI 服务。

反过来，目录很整齐也不等于真实职责清晰。若跨层隐式依赖多、状态可从任意位置写入，模型读少量文件可能建立错误假设。上下文导航应跟随调用和数据依赖，而不只按文件大小截取。

## 3. 变更合同：需求怎样成为可检查的边界

**变更合同**将目标行为、修改范围、兼容要求和验收证据明确下来。它不等于逐行规定实现，而是为模型和审查者提供共同的判断依据。

| 项目 | 要回答的问题 |
| --- | --- |
| 目标 | 改善什么行为 |
| 范围 | 哪些目录、哪些功能 |
| 非目标 | 哪些内容不动 |
| 约束 | 版本、性能、安全、兼容 |
| 验收 | 怎样证明正确 |
| 权限 | 是否允许提交、推送、发布 |
| 预算 | 模型、时间与费用上限 |

合同不是把所有未来细节锁死；发现范围不够时应说明证据并调整，而不是悄悄把小 bug 变成全量重构。

## 4. 产物与证据：为什么必须绑定同一版本

代码是产物，测试日志是对某个产物在某个环境中的观测。日志脱离代码 revision、依赖版本或输入条件，就无法支持当前交付结论。

### 图 2：证据不是一条全局“通过”标记

```mermaid
flowchart LR
    R["代码 revision"] --> E["特定环境与输入"]
    E --> T["执行检查"]
    T --> L["结果与日志"]
    L --> C["对该 revision 的有限结论"]
    R --> C
```

修改发生在检查之后时，旧证据未必继续有效。是否需要重跑取决于变更影响范围与检查覆盖，不能简单复用一句历史上的“全部通过”。

**独立审阅**也不只是让另一个模型复述作者总结。它需要访问真实差异、相关上下文和判据，并能提出可复核的问题。审阅者的独立性来自信息与方法，不只来自角色名称。

## 5. 多层验证各自证明到哪里

类型检查发现部分静态错误；单元测试检查局部逻辑；集成测试检查边界；浏览器/设备测试检查真实交互；性能测试检查代价。每种检查有盲区，不能互相冒充。

| 检查 | 主要证据 | 仍然可能遗漏 |
| --- | --- | --- |
| 类型/静态检查 | 类型与部分约束符合规则 | 业务目标或运行时输入错误 |
| 单元检查 | 局部函数和状态转换满足断言 | 外部系统与集成假设 |
| 集成检查 | 组件或服务边界协作 | 未覆盖环境与真实交互 |
| 浏览器/设备观察 | 特定路径的可见行为 | 隐藏权限和长时运行风险 |
| 人工/独立审阅 | 意图、范围、边界与证据判断 | 审阅者自身遗漏 |

这些检查相互补充，而非排列成一种可相互替代的等级。

审查应核对实际 diff、调用路径和执行证据，而不是只读模型生成的完成说明。失败日志也要保留环境信息，否则无法区分代码缺陷、依赖版本和测试环境问题。

查看异常路径、资源清理、输入校验、权限扩张、新依赖、兼容性和回退。不要让 AI 仅总结自己的 diff 充当独立 Review。

AI 输出“测试通过”不是日志；需要执行证据。不能因为修改是文档就忽略错误命令或过时安全建议。

对 Footprint：文件清单覆盖、标题层级、代码围栏、内部链接、引用来源、版本标注、图表可读性和旧结论清理分别检查。读取了所有文件不等于检查了全部事实。

## 6. 工程经验怎样回到知识库

项目实现保存具体代码，知识条目保存机制与适用条件。一次变更的价值可以提炼为状态归属、权限边界、验证盲区或故障恢复原则，而不需要把整份项目执行日志搬进知识库。

适合写回的是稳定机制与可迁移教训；项目特有路径和命令可以放带版本的“印证记录”。统一格式见 [知识条目规范](KNOWLEDGE_SPEC.md)，本页不另建第二套模板。

一次修复成功不足以证明“所有竞态都已解决”。知识条目应保存结论范围、反例和来源；敏感日志和生产凭据不属于印证材料。

怎样衡量仓库可导航性？哪些验证可以自动化，哪些必须依赖业务判断？模型如何利用编译器、测试和运行日志？这些可进入 Advance 的 AI-Native Engineering 专题，避免把工具列表当工程方法。
