# 深入模型层：后训练、蒸馏与推理系统

> 类型：Base / 模型系统。日期：2026-10-08。状态：概念审阅，参数/KV 算例的 3 条算术断言通过；无训练实验或硬件性能数据。

## 快速回顾

- 后训练改变行为，推理系统优化计算执行；应先定位失败层。
- SFT/DPO/RL 讨论目标或流程，LoRA 讨论参数化方式，不能放在同一互斥分类中。
- 权重放得下不代表服务稳定可用，容量、延迟、吞吐与质量需分别判断。

## 1. 行为适配与运行优化

不知道新事实，先检查检索和证据；格式不稳定，先检查输出契约与示例；工具使用策略持续失败，才进一步评估训练与模型选择。微调不是所有问题的默认解。

后训练改变模型行为；推理系统改变执行模型计算的方式。二者会相互影响，但问题不同：回答风格不稳定不一定需要更快 GPU；首字慢也不一定需要更多训练数据。

基础定位可先问：失败来自知识不可用、行为模式、表达约束还是运行资源？这是诊断顺序，不是任何任务都必须先 RAG 再微调的固定路线。

| 表现 | 应先核对的证据 | 可能的后续方向 |
| --- | --- | --- |
| 不知道上周更新的规范 | 是否提供最新来源 | 检索/版本维护 |
| 总是漏结构字段 | 输出合同和校验反馈 | 结构化约束、示例 |
| 同类任务持续偏离风格 | 是否有稳定、高质量示范 | 提示或行为适配 |
| 工具选择不稳定 | 描述、候选、轨迹与失败分布 | 工具设计、策略与训练 |
| 长输入首字慢 | 排队、prefill 与缓存状态 | 服务调度、缓存或输入优化 |

表格提供排查线索，不直接选定方案。若没有任务分布和失败证据，就难以判断训练是否比程序约束更有效。

## 2. 后训练目标与数据

| 方法 | 主要目标 | 所需证据 |
| --- | --- | --- |
| 预训练 / 持续预训练 | 学习通用或领域分布 | 大量合规数据与资源 |
| SFT | 模仿高质量示范行为 | 输入与正确输出/轨迹 |
| 偏好优化 | 改善相对偏好 | 可靠的偏好对及评价标准 |
| 强化学习 | 根据奖励优化策略 | 环境、奖励和采样机制 |
| 蒸馏 | 转移教师能力 | 教师输出质量与独立评测 |

SFT、DPO 和 RL 的优化目标不同。不能把“有评分”就等同于同一种强化学习流程。

SFT 通常学习示范输出的条件分布；偏好优化利用相对选择信号调整行为；RL 根据奖励与采样优化策略。DPO 通过特定偏好目标进行优化，与“在线采样、训练奖励模型再优化策略”的完整 RLHF 流程不同，但不能仅凭有无评分判断它们的理论关系。

蒸馏把教师行为或表示知识传给学生，既可能节省部署成本，也可能继承教师错误。LoRA 则改变可训练参数的参数化方式，可以用于某些适配过程；它不是与 SFT 互斥的另一种任务目标。[LoRA](https://arxiv.org/abs/2106.09685)、[DPO](https://arxiv.org/abs/2305.18290)、[InstructGPT](https://arxiv.org/abs/2203.02155)分别是不同问题的来源。

训练集需要来源许可、去重、质量筛选和污染检查。不要把测试集答案混入训练，再宣称泛化提升。模型自生成数据也会复制错误，需要验证与分布控制。

偏好数据里“看起来更长、更自信”可能被误当成更好；奖励也可能诱导捷径。先定义任务成功和禁止行为，再设计反馈。

## 3. LoRA 与参数量

LoRA 通过低秩参数化等方式减少需要训练的参数量，是参数高效适配方法，不是自动提高正确率的算法。节省多少资源取决于模型、实现与训练配置。

把一个冻结的权重矩阵 W（d_out×d_in）增量写成 B×A，其中 A 为 r×d_in，B 为 d_out×r。可训练参数量从 d_out×d_in 变为 r×(d_in+d_out)，通常还带缩放因子。

自写算例：4096×4096 的权重有 16,777,216 个参数；若 r=8，则 A、B 合计 65,536 个参数，为该矩阵原参数量的 1/256。这个比例只针对被适配的矩阵，不能说整模型显存下降 256 倍：冻结权重、激活、梯度、优化器和临时缓冲仍占资源。

选择 rank、目标层和数据覆盖后，要用保留集比较“无适配、提示改进、RAG、LoRA”。不要只报告训练 loss。

## 4. Prefill、Decode 与缓存

自回归模型常区分 prefill 与逐步 decode。长输入、长输出和并发请求会造成不同资源瓶颈。KV Cache、批处理和缓存优化的收益依赖实际工作负载。

模型参数内存、KV 状态、激活与服务开销都影响资源需求，不能只用参数量估计设备能否稳定服务。

Prefill 处理已有输入并建立相关计算状态；decode 逐步生成后续 token。并行度、内存访问和序列长度会影响瓶颈，不能把“prefill 总是算力瓶颈、decode 总是带宽瓶颈”当不受条件影响的定律。

批处理提高设备利用率，但排队可能延迟单个请求。连续批处理让不同请求在运行中加入或离开调度；前缀缓存复用兼容前缀的计算；KV 分页管理减少内存浪费。这些机制的作用对象不同。

常规 Transformer 的近似估算：

```text
KV 字节 ≈ 2 × 层数 × 每层 KV 头数 × 每头维度
          × 已缓存 token 数 × 每元素字节数 × 批中序列数
```

前面的 2 分别代表 K 和 V。GQA/MQA 的 KV 头数不一定等于 query 头数；不同长度、分页、共享前缀、滑动窗口或量化会改变实际占用。

自写假设：32 层、8 个 KV 头、头维度 128、8192 token、每元素 2 字节、1 条序列，估算为 1,073,741,824 字节，即 1 GiB。这还没有加模型权重与服务开销。长上下文与高并发会争夺容量，因此“权重放得下”不是服务可用的充分条件。

## 5. 量化、并行与资源

量化可能减少内存并改善特定硬件上的速度，但可能影响质量和算子效率。更低比特不保证任何设备都更快。部署选型要记录质量、延迟、吞吐、内存和运维成本。

权重量化减少某些参数存储；KV 量化针对缓存；激活量化有不同的算子与精度要求。低比特模型仍可能因为硬件支持、解量化和访存模式而没有预期加速。

张量并行在设备间拆分计算/参数；流水线并行按阶段分工；数据并行服务不同样本。它们涉及通信与调度，不是把模型复制到更多机器就必然线性提速。Base 在此定位概念，具体拓扑与性能模型留给 Advance。

## 6. 延迟、吞吐与质量

| 指标 | 测量区间 | 常见影响因素 |
| --- | --- | --- |
| TTFT | 请求开始到首个 token | 排队、网络、prefill、缓存命中 |
| 每 token 间隔 | 连续输出 token 的时间差 | decode、调度、传输 |
| 总延迟 | 请求到完整输出 | 输入/输出长度与工具链 |
| 系统吞吐 | 单位时间完成的 token/请求 | 并发、批处理、长度分布 |
| 尾延迟 | 如 p95/p99 | 长请求竞争、排队、重试 |

提高系统吞吐可能增加单请求等待；缩短输出可能减少总延迟却不改善首字；流式显示改善感知也不意味着模型计算更快。

PagedAttention 的核心关注点是 KV 内存管理。连续批处理、前缀缓存和 speculative decoding 分别解决不同问题，不能把名字叠加当作收益相加。投机解码还依赖草稿接受率与验证开销，应比较实际工作负载。

先固定任务集与质量下限，再记录输入/输出长度分布、并发、硬件、精度、框架版本和缓存条件。冷启动与热缓存分开；失败和超时进入分母。实验应能回答“质量保持时，哪个瓶颈被改善”，而不是只展示最快一次结果。

本章算例是理论容量估算，不是采购建议，也不宣称已有设备完成服务实测。

推理优化应该在相同任务、输入输出长度、精度与质量要求下比较。更短回答可能降低延迟，也可能丢失必要信息；更高吞吐可能增加尾延迟；更强压缩可能改变准确性。

因此容量估算帮助排除不可能的方案，真实基准帮助判断可用方案。本文理论算例不应被当成某台硬件的采购或部署保证。
