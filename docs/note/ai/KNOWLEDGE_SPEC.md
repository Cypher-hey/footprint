# AI 知识条目规范：可回顾、可查证、可扩展

> 更新：2026-10-08。适用于 AI 知识区；补充而不替代[仓库 Markdown 规范](../../../MARKDOWN_SPEC.md)。
> 目标是知识储备与印证，不以课程进度、作业或应用交付为中心。

## 1. 知识组织的最小单位

一页围绕一个有边界的问题；一个术语的主定义只维护一处。综合页负责关联，不复制所有正文。短条目可以只有几个小节，不为形式强凑十章。

新知识先决定属于：定义、机制、辨析、实现分析、经验印证还是待核查线索。它们的证据要求不同，不能把项目经验升格为普遍标准。

## 2. 推荐结构

````markdown
# 对象：本页要解释的核心问题

> 类型：Base / 专题 / Advance / 印证记录
> 范围与版本：
> 核查日期：
> 前置与主定义：
> 验证状态：

## 快速回顾
一句话定义与少量关键结论。

## 概念与边界
它是什么、不是哪些相邻概念。

## 工作机制
输入、关键步骤、状态变化、输出。

## 解释性案例
完整但有界的实例；说明真实/示意/理论算例。

## 条件、限制与误解
反例与不适用情况。

## 关联知识
前置、易混概念、应用位置、深入专题。

## 深入问题与来源
每个链接说明为什么读、看什么、不能据此推出什么。

## 更新与印证
重要修正，或已有项目的非敏感证据。
````

机制复杂时增加多个小节；速查可主要使用表格；源码分析应固定仓库、版本/提交和符号路径。模板是检查问题是否覆盖，不是要求每篇标题字面完全一致。

## 3. 图文表达选择

| 信息 | 优先形式 | 约束 |
| --- | --- | --- |
| 定义和因果 | 短段落 | 不拆成无法看出因果的碎片 |
| 同维度区别 | 表格 | 控制列数，长解释移正文 |
| 数据/控制过程 | Mermaid 流程或时序 | 箭头含义明确，图后有文字 |
| 状态与合法变化 | 状态图＋转换表 | 异步中间态、失败与未知态不偷省 |
| 数量关系 | 公式＋变量说明＋数值算例 | 写前提、单位、近似边界 |
| 张量/空间关系 | 简洁静态图或形状表 | 准确优先，避免装饰图误导 |
| 长推导/补充 | 折叠区或独立链接 | 核心定义不藏在折叠区 |
| 真实经验 | 条件—观察—结论记录 | 不补造运行结果 |

## 4. Markdown 的可移植边界

GitHub 的 Markdown 页面支持 Mermaid、数学表达式及 details 折叠，但这些支持不能自动外推到 Docute、其他静态站点或编辑器预览。

- 基础层：标题、段落、列表、表格、代码围栏、相对链接、普通图片。
- 增强层：Mermaid、公式、折叠区。必须保留文字说明或等价的可读表达。
- 不默认采用：MDX 组件、站点专属标签、可执行脚本、复杂 HTML 布局。它们会使正文依赖特定运行时。

公式可以在支持数学渲染的平台用 LaTeX，同时写明普通文本含义；图表不要只靠颜色表达正确/错误。图片写替代文字、来源与许可，外部交互图优先链接，不为展示方便嵌入任意执行内容。

官方依据：[GitHub 图表](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)、[数学](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)、[折叠内容](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections)。当前仓库站点效果另行验证。

## 5. 引用不是装饰

重要结论就近给出来源；正文末尾再提供带说明的深入入口。优先原始论文、标准、官方文档与固定源码；二手文章用于导航或不同解释视角。

| 结论类型 | 需要的依据 |
| --- | --- |
| 定义/协议 | 对应规范及版本 |
| 某库行为 | 固定代码版本、相关符号与文档 |
| 性能/质量提升 | 任务、数据、配置、对照和测量 |
| 数学估算 | 公式前提、变量、单位和算术核对 |
| 工程建议 | 适用约束与代价，不冒充定律 |
| 自定义架构 | 明确为设计示意，说明可替换点 |

论文摘要只足以支持其中明确陈述的高层贡献；具体推导、实现和性能数字需阅读对应部分。不能只打开论文首页就声称复现全部结论。

## 6. 延伸链接的写法

推荐记录“问题 → 来源 → 关注点 → 结论边界”。例如阅读 ReAct 是为了理解行动反馈对决策的作用，不是为了证明所有 Agent 必须输出某种固定思考格式。

每页少量高质量入口胜过无说明的长链接列表。内部链接标明前置、主定义、易混或深入关系；外链失效后优先寻找官方固定版本，不随意换成内容不明的转载。

## 7. 审查分层

1. 覆盖：本页承诺的问题是否真正解释。
2. 事实：重要结论是否与对应来源和版本一致。
3. 因果：解释是否跳步，类比是否越界。
4. 一致性：术语、图表、案例与其他页面是否矛盾。
5. 表达：层级、表格、代码、链接是否可读。
6. 验证：算例、协议结构和运行结果分别记录，不相互冒充。

“未运行”不能替代可完成的文献核查；“文献核对”也不能替代实际运行证据。不存在一次审查后永久正确的保证，必须允许记录限制和修正。

## 8. 实践印证与隐私

实践放在其他项目。写回本库的是结论、条件、版本、关键观察和链接；不默认复制业务数据、凭据或内部资料。链接权限也要符合知识库读者范围。

尚无证据时写“待印证”，不编造环境、耗时或成功率。一次实测只支持其覆盖的输入和版本，不扩写成无限制保证。

## 9. 借鉴哪些开源表达

- [Hello 算法](https://github.com/krahets/hello-algo)：借鉴逐步图解，不复制课程结构或未经许可复用图片。
- [D2L](https://github.com/d2l-ai/d2l-en)：借鉴数学、文字和例子的对应关系。
- [LLM Visualization](https://github.com/bbycroft/llm-viz)：作为外部交互印证；不把特定模型视图当全部模型结构。

这些参考不构成站点框架迁移决定。内容表达、站点实现与运行时配置应分别处理。

## 10. 持续维护

新增点先接入主定义与索引；形成独立问题后再拆页。Base 定义变化时检查关联专题，保留重要修正记录。版本易变的模型名、价格、上下文上限和框架 API 不应无日期地写成永久事实。

## 11. 解释质量：从“列出了”到“讲清楚了”

知识库不组织课程，不等于可以省去解释过程。面向初次理解的正文应有连续论述，速查表放在读者已建立基本模型之后；不能只靠术语索引让读者来回跳转补前提。

新增或重写时检查：

1. **问题动机**：先说明为什么需要这个概念，原来的方式在哪里不够。
2. **首次定义**：关键术语第一次出现时说明含义、所在层次和具体例子。图里的角色也必须定义；同名不同义要提醒。
3. **最小完整模型**：暂不加入无关复杂性，但必须有起点、核心过程、结果与结束。循环图要标明回到哪一步。
4. **同例贯穿**：解释、图、数据和伪代码围绕同一个例子；不要中途更换工具名称或场景而不说明。
5. **状态追踪**：说清每一步开始知道什么、谁做了什么、结束新增什么。不能用“更新上下文”四个字跳过整个机制。
6. **从例子抽象**：解释哪些是不变机制、哪些只是这个例子的参数或简化，然后再引入相邻概念。
7. **章节衔接**：每节回答一个前文自然产生的问题。小结应提炼因果，不只是再列一遍名词。
8. **复杂性分层**：幂等、并发、恢复等重要内容在基本模型建立后再加入，并说明各自补哪个缺口。
9. **图文互证**：图不能省掉正文依赖的步骤；文字不能依赖未定义图标。源码围栏闭合不代表图已经讲清楚。
10. **可理解性单独审查**：事实、格式、链接检查通过，不足以证明读者能理解。发现解释缺口应重写叙述，而不只是增加表格或字数。

[Agent Loop](03-agent-loop.md)作为本轮修订样板：问题动机、必要角色、完整回边、两次调用的输入/输出、最终退出及概念辨析。其他旧页不能因同一模板存在就自动标记为达到该解释标准。

表达参考：[Composing Programs 的迭代执行说明](https://composingprograms.com/pages/15-control.html#iteration)、[AIMA 官方 Agent 伪代码](https://aima.cs.berkeley.edu/algorithms.pdf#page=2)。借鉴解释方式，正文例子独立编写，不复制教材段落。
