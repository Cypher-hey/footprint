# AI 知识条目规范：可回顾、可查证、可扩展

> 更新：2026-10-08。适用于 AI 知识区；补充而不替代[仓库 Markdown 规范](../../../MARKDOWN_SPEC.md)。
> 目标是知识储备与印证，不以课程进度、作业或应用交付为中心。

## 1. 知识组织的最小单位

一页围绕一个有边界的问题；一个术语的主定义只维护一处。综合页负责关联，不复制所有正文。短条目可以只有几个小节，不为形式强凑十章。

新知识先决定属于：定义、机制、辨析、实现分析、经验印证还是待核查线索。它们的证据要求不同，不能把项目经验升格为普遍标准。

## 2. 推荐结构

````markdown
# 对象：本页要解释的核心问题

> 类型：Base / 专题 / Advance / 印证记录
> 范围与版本：
> 核查日期：
> 前置与主定义：
> 验证状态：

## 快速回顾
一句话定义与少量关键结论。

## 概念与边界
它是什么、不是哪些相邻概念。

## 工作机制
先给完整的最小概念模型，再逐层打开内部；解释输入、关键关系、状态变化和输出。

## 局部说明（按需）
用短例子、算例或反例澄清一个机制；不以业务案例作为整篇主线。

## 条件、限制与误解
反例与不适用情况。

## 关联知识
前置、易混概念、应用位置、深入专题。

## 深入问题与来源
每个链接说明为什么读、看什么、不能据此推出什么。

## 更新与印证
重要修正，或已有项目的非敏感证据。
````

机制复杂时增加多个小节；速查可主要使用表格；源码分析应固定仓库、版本/提交和符号路径。模板是检查问题是否覆盖，不是要求每篇标题字面完全一致。

## 3. 图文表达选择

| 信息 | 优先形式 | 约束 |
| --- | --- | --- |
| 定义和因果 | 短段落 | 不拆成无法看出因果的碎片 |
| 同维度区别 | 表格 | 控制列数，长解释移正文 |
| 数据/控制过程 | Mermaid 流程或时序 | 箭头含义明确，图后有文字 |
| 状态与合法变化 | 状态图＋转换表 | 异步中间态、失败与未知态不偷省 |
| 数量关系 | 公式＋变量说明＋数值算例 | 写前提、单位、近似边界 |
| 张量/空间关系 | 简洁静态图或形状表 | 准确优先，避免装饰图误导 |
| 长推导/补充 | 折叠区或独立链接 | 核心定义不藏在折叠区 |
| 真实经验 | 条件—观察—结论记录 | 不补造运行结果 |

## 4. Markdown 的可移植边界

GitHub 的 Markdown 页面支持 Mermaid、数学表达式及 details 折叠，但这些支持不能自动外推到 Docute、其他静态站点或编辑器预览。

- 基础层：标题、段落、列表、表格、代码围栏、相对链接、普通图片。
- 增强层：Mermaid、公式、折叠区。必须保留文字说明或等价的可读表达。
- 不默认采用：MDX 组件、站点专属标签、可执行脚本、复杂 HTML 布局。它们会使正文依赖特定运行时。

公式可以在支持数学渲染的平台用 LaTeX，同时写明普通文本含义；图表不要只靠颜色表达正确/错误。图片写替代文字、来源与许可，外部交互图优先链接，不为展示方便嵌入任意执行内容。

官方依据：[GitHub 图表](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)、[数学](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)、[折叠内容](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections)。当前仓库站点效果另行验证。

## 5. 引用不是装饰

重要结论就近给出来源；正文末尾再提供带说明的深入入口。优先原始论文、标准、官方文档与固定源码；二手文章用于导航或不同解释视角。

| 结论类型 | 需要的依据 |
| --- | --- |
| 定义/协议 | 对应规范及版本 |
| 某库行为 | 固定代码版本、相关符号与文档 |
| 性能/质量提升 | 任务、数据、配置、对照和测量 |
| 数学估算 | 公式前提、变量、单位和算术核对 |
| 工程建议 | 适用约束与代价，不冒充定律 |
| 自定义架构 | 明确为设计示意，说明可替换点 |

论文摘要只足以支持其中明确陈述的高层贡献；具体推导、实现和性能数字需阅读对应部分。不能只打开论文首页就声称复现全部结论。

## 6. 延伸链接的写法

推荐记录“问题 → 来源 → 关注点 → 结论边界”。例如阅读 ReAct 是为了理解行动反馈对决策的作用，不是为了证明所有 Agent 必须输出某种固定思考格式。

每页少量高质量入口胜过无说明的长链接列表。内部链接标明前置、主定义、易混或深入关系；外链失效后优先寻找官方固定版本，不随意换成内容不明的转载。

## 7. 审查分层

1. 覆盖：本页承诺的问题是否真正解释。
2. 事实：重要结论是否与对应来源和版本一致。
3. 因果：解释是否跳步，类比是否越界。
4. 一致性：术语、图表、案例与其他页面是否矛盾。
5. 表达：层级、表格、代码、链接是否可读。
6. 验证：算例、协议结构和运行结果分别记录，不相互冒充。

“未运行”不能替代可完成的文献核查；“文献核对”也不能替代实际运行证据。不存在一次审查后永久正确的保证，必须允许记录限制和修正。

## 8. 实践印证与隐私

| 字段 | 保存什么 |
| --- | --- |
| 待印证的知识结论 | 指向主条目中的具体命题 |
| 条件与版本 | 项目、提交、环境、输入、范围 |
| 观察证据 | 可核对日志、状态变化或产物 |
| 支持范围 | 观察实际支持哪些结论 |
| 未覆盖与反例 | 尚未验证、失败或不适用条件 |
| 回流位置 | 应修订的主条目与关联链接 |


实践放在其他项目。写回本库的是结论、条件、版本、关键观察和链接；不默认复制业务数据、凭据或内部资料。链接权限也要符合知识库读者范围。

尚无证据时写“待印证”，不编造环境、耗时或成功率。一次实测只支持其覆盖的输入和版本，不扩写成无限制保证。

## 9. 三种表达思路怎样组合

| 参考 | 借鉴的组织方式 | 在本库如何落地 | 不直接照搬 |
| --- | --- | --- | --- |
| [Jay Alammar](https://jalammar.github.io/illustrated-transformer/) | 从整体到局部的渐进图解 | 先外部边界，再角色/内部机制，再反馈或约束 | 特定架构配置、原站图片 |
| [Aman’s AI Journal](https://aman.ai/primers/ai/transformers/) | 细粒度知识条目与可检索组织 | 清晰小节、概念对照、唯一主定义 | 过密目录或同页无限堆叠 |
| [Lilian Weng](https://lilianweng.github.io/posts/2023-06-23-agent/) | 专题关联、问题展开与引用 | 说明相邻概念关系，来源附阅读目的 | 历史研究结论无条件当现状 |

三者组合后的阅读层次是：快速回顾 → 连续概念论述与渐进图解 → 边界和关联 → 注释来源。文章主线始终是概念之间的因果与关系，不以某个用户、文件或业务案例贯穿所有小节。

[D2L](https://d2l.ai/)可补充数学与解释之间的对应，[LLM Visualization](https://github.com/bbycroft/llm-viz)可作为外部交互印证。这些参考不构成站点迁移或依赖引入决定；本文不复制原站内容和配图。

## 10. 持续维护

新增点先接入主定义与索引；形成独立问题后再拆页。Base 定义变化时检查关联专题，保留重要修正记录。版本易变的模型名、价格、上下文上限和框架 API 不应无日期地写成永久事实。

## 11. 解释质量：先形成概念模型，再帮助回顾

知识库不组织课程，不等于省略解释过程。新读者需要连续论述建立模型，熟悉者需要标题、回顾和表格快速定位；两种需求应在同一页面兼容。

1. **问题动机**：为什么需要该概念，它补哪个认知缺口？
2. **首次定义**：核心术语出现时说明含义与层次；来自其他页的术语给最短必要解释和主定义链接。
3. **最小完整模型**：先表达全部关键关系，再增加复杂性。循环必须标明回到哪一步及停止边界。
4. **概念主线**：小节围绕对象、关系、机制和条件推进，不以某个案例发生的时间顺序组织全文。
5. **渐进图解**：后图应明确打开前图的哪个部分，或补充哪个维度。不要画多张内容相同、只改标签的流程图。
6. **局部例证**：例子只解释一个难点，用完回到概念；同一例子内部名称保持一致，但不要求全章沿用一条案例。
7. **图文互证**：图前说明要解决的问题，图后说明箭头、变化和边界。即使 Mermaid 未渲染，正文仍能表达核心机制。
8. **跨章连续**：开头交代承接，结尾说明接续；定义、条件与术语主归属见 [知识地图](KNOWLEDGE_MAP.md)。
9. **避免复写**：保留必要提醒，完整机制只维护一次。综合页做关系整合，不复制基础教材。
10. **解释与验证分开审查**：格式正确不证明讲清楚，引用存在不证明结论成立，算例通过不证明实际系统可用。

[03 Agent Loop](03-agent-loop.md)是概念主线与渐进图解的样板；其他章节采用相同原则，但不强制相同节数、图数或篇幅。更复杂的章节可以更长，简单概念不靠重复填充。

## 12. 提交前的跨章检查

- 新术语是否已有主定义？同词异义是否明确，如 policy、decode、grounding？
- 本页声称覆盖的问题是否在正文真正展开，而不只是列一个链接？
- 图中的角色、箭头、状态与正文是否一致？简化假设是否说明？
- 其他章节是否复制了完整机制？是否可替换为一句衔接与链接？
- 核心内容是否依赖某个案例才能理解？抽掉例子后概念关系是否仍完整？
- 目录、术语入口、Advance 前置和审阅状态是否同步？
- 所声称的检查是否真的执行？未渲染、未联调和未实测是否分别记录？

教材表达参考：[Composing Programs 的迭代说明](https://composingprograms.com/pages/15-control.html#iteration)、[AIMA 官方 Agent 伪代码](https://aima.cs.berkeley.edu/algorithms.pdf#page=2)。借鉴清晰定义与机制解释，不复制教材段落。

## 9. 三视图条目约定（样板）

2026-10-10：03 的三个样板使用纯 Markdown 的四个二级标题，顺序固定：

1. 先用这条主线回答：3–5 条定义、机制、边界结论，始终可见。
2. 完整口语答案：连贯解释，适合理解与复述，不伪造项目经历。
3. 书面精讲：完整主定义、机制、对比、误区、来源；内部从三级标题开始。
4. 概念图解：整体关系、局部职责和流程，每图有文字结论及稳定锚点。

三种表达共享知识结论，不能各说一套；图源仅在图解区维护，正文通过锚点引用。一个概念的主解释只在一个条目，其他专题保留简短定位与链接。不是每个概念都强求相同图数或章数。

网站通过本地阅读增强脚本识别完整结构；未满足结构的普通页面保持原样。GitHub、脚本加载失败、打印时仍应可读完整内容。网站的偏好仅保存视图选择，不代表用户学会某个知识点。

详细验收与已知限制见[样板说明](../../implementation/READING_SAMPLES.md)。
