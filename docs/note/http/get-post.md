# GET 与 POST：先理解语义，再讨论传参

> 适用：HTTP API 设计与浏览器请求。核查日期：2026-10-08。
> 状态：规范对照与示例静态审阅；示例未执行。

## 1. 导读与核心结论

GET 表达读取目标资源的表示，POST 表达让目标资源处理提交的内容。核心差异是语义，不是“GET 走 URL、POST 走 body”。

| 维度 | GET | POST |
| --- | --- | --- |
| 安全语义 | 不请求业务状态变更 | 可以请求业务状态变更 |
| 幂等语义 | 是 | 不保证 |
| 常见输入 | 路径、查询参数、请求头 | 路径、查询参数、请求头、请求体 |
| Cookie | 满足浏览器策略时可携带 | 满足浏览器策略时可携带 |
| 响应缓存 | 常见，仍受缓存策略限制 | 规范允许特定条件下缓存，实际支持不能假定 |
| 保密性 | 方法本身不提供加密 | 方法本身不提供加密 |

“安全”不代表服务端不能记访问日志；“幂等”也不代表每次响应内容完全相同。

## 2. 为什么不能用 GET 修改收藏

假设 GET /favorite?id=42 会新增收藏，链接预取、爬虫、重试或用户刷新就可能触发写操作。应把读取与变更分开：

```http
GET /api/cards?tag=agent
POST /api/favorites
Content-Type: application/json

{"cardId":"42"}
```

这是接口设计示例，不是对真实服务的调用。

POST 请求也可以带查询参数；body 用什么编码由 Content-Type 与接口契约决定。浏览器 Fetch 不允许 GET/HEAD 请求携带 body，不应依赖某个服务端的私有约定突破互操作边界。

## 3. 长度与安全边界

HTTP 并没有一个适用于所有产品的“GET 固定 2 KB 上限”。浏览器、网关和服务器有各自限制；POST 的 body 同样受大小、超时与配额限制。

敏感数据不应放在 URL：URL 可能进入历史、日志和分享链接。换成 POST 仍需要 HTTPS、身份验证、授权、输入校验和日志脱敏。

## 4. 重试设计

生成草稿或下单发生超时后，客户端不知道服务端是否已完成。盲目重试 POST 可能重复创建。可由业务定义幂等键、保存操作结果、提供状态查询。幂等键的作用域、过期时间、同键异参冲突都应写进契约。

## 5. 自测

1. GET /delete?id=1 为什么不符合 GET 的安全语义？
2. 两次 GET 返回的更新时间不同，是否违反幂等？
3. POST 超时后，怎样判断该重试还是查询状态？

参考答案：方法与行为不一致；不违反，幂等关注请求的预期效果；依赖业务操作 ID、幂等记录及查询协议，不能凭超时推断失败。
