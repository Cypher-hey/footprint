# 移动 Web 性能：指标、预算与体验

> 核查日期：2026-10-08。状态：方法更新；无真实设备数据。

## 1. 先定义体验

Core Web Vitals 当前关注 LCP、INP、CLS，分别反映加载、交互和视觉稳定性。还需结合业务首屏、可用时间、错误率、内存与耗电等指标。

指标阈值和统计口径按官方资料核查；不能把某篇旧笔记的“3 秒”直接当作所有产品的合格标准。

## 2. 资源预算不是简单乘法

旧文以单一网速乘三秒推导全部资源预算，遗漏往返、拥塞、连接、解析与关键路径。还混淆了 bit 与 byte 风险。预算应结合真实设备、网络分布和瀑布图制定。

## 3. 请求与协议

HTTP/2/3 多路复用改变请求成本，不能套用“首次最多四个资源”的通用规则。合包可减少请求，但过大的包会影响缓存、解析和按需加载；按业务边界权衡。

## 4. 常见优化

| 瓶颈 | 候选措施 | 风险 |
| --- | --- | --- |
| 图片太大 | 合适尺寸、压缩、现代格式 | 画质、兼容、解码成本 |
| JS 太重 | 分包、延迟非关键代码 | 碎片过多、请求瀑布 |
| 响应慢 | 缓存、减少串行依赖 | 过期或私有数据泄露 |
| 主线程拥堵 | 减少同步工作、合理调度 | 过度异步增加复杂度 |
| 布局跳动 | 预留尺寸、稳定占位 | 占位与实际内容不匹配 |

## 5. 交互和耗电

不要全局滥用 will-change 或不断运行的动画。页面不可见时评估是否应暂停工作。长列表、频繁事件和大图解码都可能影响流畅度，不能仅以“开启 3D 加速”解释。

## 6. 练习与验收

分别测冷启动、缓存访问、滚动和连续操作；查看分位数而不只看单次平均值。证明优化改善了目标指标，且没有损害功能与无障碍。
