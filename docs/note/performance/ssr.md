# CSR、数据直出与 SSR：比较关键路径和维护成本

> 核查日期：2026-10-08。状态：架构知识说明；未进行部署或性能对照。

## 1. 三个概念

| 方式 | 初始返回 | 客户端工作 |
| --- | --- | --- |
| CSR | 页面壳与脚本 | 获取数据并生成 UI |
| 数据直出 | 页面壳与初始数据 | 用数据生成 UI |
| SSR | 服务端生成的 HTML | 可能需要 hydration 接管交互 |

框架也可以混合静态生成、流式 SSR 和客户端组件。SSR 与前后端职责分离不是互斥概念。

## 2. 为什么可能更快

减少客户端串行请求，或更早交付可显示内容。但服务端数据慢、HTML 太大、hydration 脚本重时，收益可能抵消。内网也不天然“极快且稳定”。

## 3. 看见与可交互不同

服务端返回 HTML 后用户可能看见内容，但按钮交互仍需客户端准备。需要同时观察服务器响应、内容绘制、hydration 成本和交互延迟。

## 4. 数据注入安全

不能把任意对象直接拼进 HTML 属性或 script 标签。JSON 序列化不自动解决所在 HTML 上下文的转义；应使用框架提供的安全机制，并避免暴露服务端秘密。

## 5. 一致性

初始客户端渲染应与服务端输出兼容。随机数、时间、浏览器专有 API 和用户环境差异可能造成 mismatch。副作用执行位置、缓存隔离和错误恢复都要设计。

## 6. 选择依据

内容型页面、搜索可见性、低端设备、实时个性化、部署复杂度与缓存策略会影响选择。没有一条“SSR 一定更快”的结论，也没有所有页面通用的 1000 KB 首屏标准。

## 7. 验证练习

为相同内容比较 CSR 与 SSR：固定网络和设备，记录服务端等待、LCP、JS 执行、交互可用时间和缓存命中。不要只对比截图出现时间。
