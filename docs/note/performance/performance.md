# Web 性能基础：先测瓶颈，再选优化

> 核查日期：2026-10-08。状态：旧结论纠错；未做性能基准。

## 1. 不靠 API 名称判断性能

innerHTML 需要解析，DOM API 也有成本，哪种更快取决于规模和操作方式。处理不可信内容时先考虑安全；纯文本使用 textContent，不能为性能把外部字符串直接当 HTML。

## 2. 集合是否实时要看具体 API

HTMLCollection 常为 live；NodeList 可能静态也可能 live，例如 querySelectorAll 返回静态列表。不能说所有 NodeList 每次访问都重新查询文档。

## 3. 脚本与解析

经典脚本、defer、async 和 module 的下载与执行时机不同，不能把所有 script 都描述成同一种阻塞流程。脚本执行仍可能占用主线程，应按真实轨迹诊断。

## 4. 监听器与内存

移除 DOM 节点不会天然造成泄漏；垃圾回收取决于是否仍可从存活根到达。保留闭包、全局集合、订阅或定时器可能使节点继续存活。

事件委托可减少监听，但不是所有事件和交互都适合。资源生命周期应明确，必要时移除监听或使用 AbortSignal。

## 5. 页面闪烁

FOUC 不只发生在 IE。样式到达时机、客户端主题初始化、动态注入和 hydration 都可能影响首次显示。优化应平衡首屏、缓存与可维护性，而不是一律禁用某种语法。

## 6. 实践与练习

先保存基线：页面、设备、网络、输入数据和交互路径。改变一个因素后复测，检查是否引入内存或可访问性回归。

练习：证明一个 NodeList 是静态还是实时；录制长任务；用堆快照或引用链判断节点为什么没释放。
