# JavaScript 性能：不要沿用旧引擎微优化结论

> 核查日期：2026-10-08。状态：历史结论审阅，无新基准数据。
> 原文大量引用 Opera 9、早期 IE 的比例和经验，本次不再将其作为现代引擎推荐。

## 1. 稳定原则

减少不必要的工作、选择合适算法、限制数据规模、避免主线程长任务，通常比机械替换某个表达式更有价值。正确性、安全与可维护性优先于未经测量的微优化。

## 2. 逐项纠错

| 旧说法 | 当前正确的理解 |
| --- | --- |
| eval 固定慢 100 倍 | 没有跨环境固定比例；还存在代码注入与优化限制 |
| 高频函数不能用 try/catch | 不能为历史性能传言移除必要错误处理 |
| new String 能避免装箱更快 | 不作为推荐；包装对象还改变类型与相等语义 |
| += 分两次一定更快 | 引擎优化与数据规模不同，必须测 |
| 数组下标写入一定胜过 push | 不保证，选择清晰且正确的 API |
| Math.min 总等价于三元表达式 | NaN、类型转换和负零等边界需考虑 |
| 局部变量退出就立即释放 | 回收取决于可达性与闭包等因素 |
| 定时器最小延迟固定 10–100ms | 嵌套、后台、平台策略和主线程忙碌均有影响 |

## 3. 代码生成与安全

动态字符串执行不是普通数据处理。优先使用函数、属性访问、解析器或受限解释器；不要把外部输入直接交给 eval、Function 或字符串定时器。

## 4. 遍历选择

for...in 面向可枚举字符串属性，还会遍历原型链；数组值遍历通常使用 for...of、数组方法或索引循环。选择首先由语义决定，而不是笼统“某循环最快”。

## 5. 基准怎样做

固定引擎版本、输入规模、冷/热状态与重复次数；防止死代码消除和无效微基准。看真实业务占比，微小局部收益不一定改善页面体验。

## 6. 自测

一个 O(n²) 算法换成更短语法后快了 5%，是否值得停止优化？先比较更合适的数据结构，再评估真实输入规模和可读性。
